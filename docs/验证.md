- CherryUSB 候选在 EP0 心跳失败时记录阶段、ESP 错误、URB raw 结果、可信时的传输/描述符长度、descriptor 头、锁等待/URB/总耗时，以及可用的输入计数、设备 epoch/连接状态快照。未执行或不可用的数据输出 `unknown`；失败 URB 的 `actual_length` 不可当作有效长度。
- 失败事件保存在 RAM 最近 8 条历史中，成功不会覆盖历史；设备重启会清空这些记录。每 60 秒串口重放历史时，`HB_DIAG replay=1` 表示同一事件的重放，不能作为新失败计数。`HB_RECOVER` 记录连续心跳失败后首次成功的失败数和跨度，不代表鼠标实际冻结或用户可见停顿时间。
- 不需要为这项诊断一直后台监听：怀疑发生过失败后，可在保持设备不复位的前提下被动捕获 65 秒以上，等待串口重放当前 RAM 最近 8 条；若关闭串口期间设备重启，RAM 历史会丢失。
- 部署该候选后应在 921600 baud 串口被动采集至少 65 秒，以覆盖 60 秒历史重放和 5 秒摘要；只读打开串口必须在 `open()` 前后确认 DTR/RTS 为 false。检查 `HB_DIAG`、`HB_RECOVER`、5 秒分类摘要中的 `stack_hwm` 及 WDT 输出。串口由 Host 占用时不得抢占或终止 Host 进程。
- EP0 `GET_DESCRIPTOR` 心跳用于检查控制通路，不证明 interrupt-IN 报告仍在到达；聚合的多接口输入计数也不证明每个接口都没有丢报。不要把单独的 `ESP_ERR_NOT_FOUND` 等同于物理断连；需结合有效设备状态快照和失败阶段解释。
- 候选 app SHA-256 `67CD96A3AFB827A72E862209EF9AC81EE3EE83C25B5347BDFCF132103733D084` 已仅刷入 M/COM13，三段均 `Hash of data verified`；P 未刷未复位。安全统计打开前后 DTR/RTS 均低。实际部署文件、flash args 和恢复镜像副本见 `artifacts/tests/cherryusb-hb-diagnostic-flash-20261011-184312/`。

## 设备统计快照读取

```powershell
python .\tools\read_device_stats.py
```

固件在 RAM 中保存恢复计数，通过 UART0 请求 `0x1D` 读取一次性分页快照、`0x1E` 返回计数器与队列记录。独立读取需在 **Host EXE 未占用**的串口上运行；Host 界面里的“读取设备统计”复用已打开的 M/P 串口。字段定义见 [协议说明](protocol.md)。

**查询默认不触发复位**（项目规则，见 `AGENTS.md` 的「串口查询默认不触发复位」）：打开串口前先把 `DTR` 与 `RTS` 置低，再 `open()`，打开后可再确认一次电平；不要使用 `serial.Serial(port, baud)` 这种带端口直接打开的写法——pyserial 会在打开瞬间拉高这两根线，经板卡自动复位电路复位设备。

```python
ser = serial.Serial()      # 不指定 port，构造时不打开
ser.port = port_name
ser.baudrate = baud
ser.dtr = False            # 必须早于 open()
ser.rts = False
ser.open()
ser.dtr = False
ser.rts = False
```

为什么必须这样：统计计数**只存在于 RAM**，一次意外复位就会把累计值清零、并打断 USB 链路与克隆，于是"查询动作本身"会毁掉你要观察的对象。

**每次查询都要自证没有复位**：把设备上报的 `uptimeMilliseconds` 与查询的墙钟时间对照，uptime 应随时间连续增长（两次查询之间 uptime 的增量应约等于墙钟间隔，反推的开机时刻不变）。发现 uptime 归零或明显偏小，就说明中间发生了复位，该次数据只能按"复位后窗口"解读并在记录里标注。

参考实测（2026-10-08，两次读取间隔约 250 s）：uptime 217.8→469.7 s（P）/220.2→467.6 s（M），反推开机时刻漂移 0.0 s，证明读取未触发复位。当前工具实现情况：`tools/read_device_stats.py`、`tools/test_makcu_v4.py`、`tools/test_dual_proxy_serial.py`、`tools/dual_uart_inspect.py`、`tools/capture_dual_serial.py`（其中的显式 `hard_reset()` 属有意例外）、`tools/uart1_soak_monitor.py`、`tools/vendor_control_probe.py`、`tools/inject_mouse_motion.py`、`tests/hardware/mouse_20ms_check.py` 均已按此方式打开端口；本机未跟踪的探针 `firmware/usb_bandwidth_probe/benchmark.py` 仍是先打开再操作 DTR，使用它会复位板卡，不要用它做只读查询。

## 结论边界

- Windows PnP 节点存在只能证明当前枚举存在，**不等于**厂商驱动（如 G HUB）识别成功。
- 固件记录到 USB report submit/complete，只能证明板端提交完成，**不等于**接收电脑的应用或光标已消费。
- 打开 CH340 调试口进行采集会经 DTR/RTS 触发对应板复位，采集结果必须标注这一扰动。
- 串口号随拔插变化，每次采集前重新确认角色与端口；同一端口同一时刻只允许一个程序占用。
- 模拟测试、单元测试、构建验证、端到端验证与真实设备结果必须分别记录，不得互相替代。

## 随机断连与恢复状态

- 鼠标**随机断连（偶发无响应）仍会出现**：根因是 upstream ESP-IDF USB Host 缺陷（IDFGH-14198 / issue #14996，官方未修）。当前版本以「冻结检测 → 根端口断电重枚举」自愈兜底，**断开→恢复已压缩到 1 秒以内**（用户确认；2026-10-08 只读复查的 15 分钟窗口里 3 次恢复中有 2 次检测延迟 ≤500 ms，即 `late500=1`）。因此它是"会发生但基本无感"，**不是"已消除"**。相应的分析与排查文档已按结论移除，历史边界保留在[审计记录](审计.md)；判据与计数含义见[固件说明](固件.md)的「USB Host 冻结检测与恢复」。
- 长时 1 kHz 压力、Windows 重启顺序、真实目标端消费与厂商驱动初始化等场景仍需逐项实测，未验证项以[审计记录](审计.md)的清单为准。
