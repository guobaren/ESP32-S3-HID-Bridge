## 本轮更新（2026-08-06，7.5 ms 可用性评估）
- + 当前传统 BLE 连接间隔以 1.25 ms 为单位，7.5 ms 是基线连接间隔下限；本项目参数请求范围已经是 7.5–10 ms。
- + 最新真实日志证明 Windows Central 最终选择 10 ms，而不是 7.5 ms；Peripheral 只能请求范围，不能强制 Central 采用最小值。
- + 可进一步试验 `min=max=7.5 ms、latency=0`，但存在被 Windows 拒绝、重新改为 10/20 ms或增加连接稳定性风险，必须以最终 `conn_update_final` 为准。
- + 7.5 ms 是连接事件间隔，不等于鼠标端到端延迟固定为 7.5 ms；主机采集、固件排队、事件相位、无线重传和 Windows 输入栈仍会增加延迟与抖动。

## BLE 报告率原因结论（2026-08-06）

- 用户问题：资料称 BLE 鼠标可达数百 Hz，而本项目实测约 100 Hz。
- 结论：当前瓶颈首先是 BLE/HOGP 的实际到达节拍与 Windows 分发节拍，不是鼠标 X/Y 字段容量。
- 真实对端数据：`artifacts/ble-trace.summary.txt` 为 30.030 秒、3306 个 Raw Input 事件，平均 `110.08 Hz`；中位数间隔 `14.268 ms`、P95 `15.036 ms`、最大间隔 `165.349 ms`，且存在大量短间隔成簇到达。
- USB 同条件对照：`artifacts/usb-trace.summary.txt` 平均 `319.95 Hz`、中位数间隔 `2.022 ms`；因此“约 100 Hz”是 BLE 路径的实测现象。
- 固件在 `firmware/main/esp_hid_gap.c:40-42` 和 `:898-900` 只是请求 `7.5–10 ms` 或 `7.5–15 ms` 的连接间隔范围；请求值不等于 Windows 中心最终协商值。
- 固件已在 `firmware/main/esp_hid_gap.c:936-940`、`:978-989` 打印实际连接参数，但目前尚未取得包含该行的有效串口日志，不能把最终 connection interval 写死为某个值。
- 解释边界：BLE 5/2M PHY 提高吞吐不等于自动提高 HID 报告频率；宣传的 400/800/1000 Hz 可能依赖厂商高速模式、专用接收器、不同连接参数或多报告/连接事件，不能直接与普通 Windows HOGP + ESP32 NimBLE 路径比较。
- 下一步：重新采集连接建立后的串口日志，确认 `negotiated connection parameters: interval=...`；再按该值、发送失败/积压统计和对端 Raw Input 时间戳区分固件调度、BLE 空口/重传与 Windows 分发因素。

## 主机端“最大积压”解释（2026-08-06）

- 用户日志中 `最大积压=(241,32)` 不是当前待发送量，也不是积压了 241 个报告；它是 `_maxPendingX/_maxPendingY` 记录的会话内历史峰值，只有 `ResetStateLocked()` 时清零。
- `MouseReportPump.Accumulate()` 每收到 Raw Input 就把 delta 累加到 `_pendingX/_pendingY`，并立即用 `Math.Abs(_pendingX/Y)` 更新最大值（`host/HidBridge.Host/Input/MouseReportPump.cs:91-110`）。
- 发送线程每 2 ms 执行一次，但只有非零位移/按钮变化时才真正提交报告；发送时从 pending 中扣除本次报告值（`MouseReportPump.cs:154-190`）。因此某次输入突发、定时器延迟、发送锁等待或传输阻塞都可能让 X 暂时累计到 241，之后又回到 `待发送=(0,0)`。
- 日志两次统计间隔约 5 秒，原始事件增加 4893，提交报告增加 1733；后者是有内容的报告数，不是每个 2 ms tick 都提交报告。最大积压是该期间任意时刻峰值，不能用最终待发送值反推。
- 该值说明主机端某个时刻输入产生速度高于发送端消化速度，但单独不能证明 BLE 空口造成；需要同时看 `提交间隔us`、传输 Send 阻塞时间和固件端 pending/发送失败统计。

## BLE 平滑与低延迟优化建议（2026-08-06）

### 推荐优先级
1. 先采集同一连接会话的最终 `negotiated connection parameters`，确认真实 interval；不以请求的 7.5–15 ms 代替实测值。
2. 将 `firmware/main/ble_output.c:166` 的固定 `vTaskDelay(8 ms)` 改为基于连接 interval 的 `vTaskDelayUntil` 或任务通知唤醒 + 节拍限流，避免固定 8 ms 与 BLE connection event 错位和任务漂移。
3. 将 `BLE_MOUSE_MAX_MOTION_PER_REPORT` 从无条件 `INT16_MAX` 改成“低积压小步、积压超时自动放大”的自适应上限，优先减少正常移动的跳变，同时防止大范围移动形成不可接受的排队延迟。
4. 若实际 interval 大于 7.5 ms，单独测试固定请求 `7.5–7.5 ms, latency=0`；保留 Windows 实际协商结果和稳定性对照，不能只看请求是否成功。
5. BLE-only 条件下暂时关闭 Wi-Fi 输入/配网功能做 A/B 对照；ESP32-S3 的 BLE/Wi-Fi 共存可能放大节拍抖动，但不能在未测试前直接归因。

### 取舍
- 仅增加发送频率不会创造新的输入信息，可能把 BLE 队列推满并造成更严重成簇。
- 仅把单帧上限改成 `INT16_MAX` 会降低大范围移动的排队延迟，但积压一次发送会形成更大跳变；应改为自适应上限。
- 插值只能改善显示观感，不能消除真实 HID 报告延迟；优先解决协商 interval、发送节拍和成簇问题。

- 本轮未修改固件，建议先按上述 1→2→3 顺序实施并重新烧录；真实设备结果仍需 BLE/USB 同条件 CSV 与串口统计分开判定。

## 2.4G 接收器方案评估（2026-08-06）

- 结论：可以增加“2.4G 专用接收器”连接形式，但不是在当前 ESP32-S3 固件中打开一个现成的标准鼠标模式即可完成。
- ESP32-S3 硬件本身支持 2.4 GHz Wi-Fi、Bluetooth LE 和 USB Device；可用 ESP-NOW 建立自定义 2.4G 点对点链路，并由另一块带 USB Device 的 ESP32-S3 作为 USB HID 接收器接入电脑。
- 推荐拓扑：现有 ESP32-S3（发送端） -> ESP-NOW 自定义报告 -> 第二块 ESP32-S3 USB 接收器 -> Windows USB HID 鼠标。
- 不建议直接把普通 Wi-Fi/ESP-NOW 报文当作 Windows 鼠标；电脑必须看到 USB HID 接收器，或者安装主机端程序，不能依赖 Windows 原生 BLE HID。
- 若目标是兼容现成商业 2.4G 接收器，通常无法直接复用，需要逆向厂商私有协议；更可控的是自建配对、序号、确认/重传和丢包检测协议。
- 该方案理论上可避开当前 BLE connection interval 和 Windows BLE HID 分发瓶颈，但实际刷新率、延迟和稳定性必须用第二块接收器做真实端到端测量，不能仅凭 ESP-NOW 链路吞吐宣称达到 500/1000 Hz。

### 特殊指令

- 主机保持 `portName: "auto"` 即可；若同时连接 CH340 和原生 CDC、且要强制测试 CDC，可临时把端口固定为新枚举的 CDC COM，测试后恢复原配置。
- 原生 USB CDC 的 `921600` 只是 Windows `SerialPort` 的 line coding 兼容参数，不代表 USB 总线实际按 UART 波特率传输。
- 使用原生 CDC 输入时先连接 BLE 并确认蓝灯后再按 `HOME`；BLE 未就绪时 USB HID 回退会把报告送回输入电脑，可能形成输入回路。
- 当前 ESP-IDF 构建需使用 Python 3.12 环境并设置 `ESP_IDF_VERSION=6.0.2`；默认便携 Python 3.9 的 `export.ps1` 路径仍可能失败。
- 模拟、单元、构建和真实设备结果必须分开记录；COM 出现、灯亮、EXE 正常退出都不能单独判定端到端通过。
