## 当前目标

## 关键教训与已撤回结论（不要重犯）

- **已撤回/作废**（原「故障排查总结」已删除，结论保留在本条）：移动浅队列（8 槽 + 满则清空）→ 实测丢弃过多、手感明显变差；"移动合并成一条" → 报告率压到约 30 Hz；"同 Profile 沿用现有克隆" → 按要求必须完整卸载+重装；"主机 EXE 用 DTR/RTS 复位板子" → 代码级否证；"板载写盘饿死控制传输" → A/B 否证；"移动是超时主因""移动占满 IO" → 受控 A/B 否证；"固件合成 HID++ 回复" → 实为我 function 位写错；探针"OUT 端点永久阻塞" → 阻塞 I/O 造成的假象。
- **下结论前先自证测量手段**：让路判据三次空转、预热期打点漏赋值（日志里超时值仍写 800 ms 才暴露）、`ctypes` 未声明 `restype` 截断 64 位句柄、用中文过滤乱码控制台输出——都因此返工。
- **警惕死代码**：`on_mouse_report` 这类"永不被调用"的回调曾让一个机制长期空转；给机制加**可观测计数**是发现空转的唯一可靠办法。
- **区分"板子卡"与"设备没答"**：看超时窗口内 1 Hz 统计与链路统计是否照常输出。
- **区分"拥堵"与"个别失败"**：看成功那批的耗时分布（`ctrl_lat_max_us`/`slow10`），而不是只看失败计数。
- **同一时间窗口内的相关性不是因果**：必须用受控 A/B（移动/超时曾同处一个窗口而误导判断）。
- **先核对任务书里的数字，再动手实现**（2026-09-28 教训）：交接里"Profile 全量重传恒定 1070 ms"驱动了一个协议级改造计划，复核 40+ 份真机日志后发现数据段只有 12~30 ms，那 1070 ms 是"1 s COMMIT 重试间隔 + 提前成功 ACK"的测量假象。**凡是要为某个耗时做优化的前提，先用现成日志把该耗时本身量出来**。
