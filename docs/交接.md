## 当前目标

两块 ESP32-S3 组成透明桥：**鼠标侧板（M）** 用原生 USB 接真实罗技鼠标并动态采集其 USB 描述符（Profile），
经板间 UART1 传给 **电脑侧板（P）**；P 用 TinyUSB **严格克隆**出一个鼠标设备供接收端电脑与 G HUB 使用，
并把 G HUB 的 HID++ 控制请求（EP0 控制传输）转发给物理设备。目标是任意接线顺序、任意单板复位/断电后
都能自行恢复，接收端看到的就是"那只鼠标"。

当前主线：**消除"设备偶发不完成控制传输"的影响**。成因已定位到设备侧（约 10%/次复位，未解），
我们这一侧已做到「不锁死 + 自动恢复 + 全程可观测」，并把复现率压到 8/9 次复位完全干净。

### 最新实测（截至 2026-09-25）

- **连续 9 次复位：8 次完全干净，第 9 次按设计自愈**（超时 → 一级重挂 → 端口断电 → 克隆重建，`收到Profile ACK：transfer=2`）。复现率与上一轮 1/6 同量级。
- **"移动占满 IO"被直接否证**：同一探针压力下 A 静止与 B 快速移动（58146 条 ≈1.1 kHz）对比，控制传输均为 `388/388` 成功、`ctrl_lat_max_us=8999`、`slow10=slow100=0`。
- 稳态刷新 `p50 = 1.01~1.14 ms`（约 1 kHz）；悬空（左键按住、鼠标离桌）7.5 s 内位移 0 次。
- 移动延迟验收（`tools/measure_udp_smoothing.py`）：单次首动 `5.998/6.999 ms`、连续首动 `3.999/5.0 ms`，位移 `20px`/`60px` 精确一致。
- 单板复位恢复：P 复位→挂载约 `1.6 s`、M 复位→挂载约 `2.0 s`；PnP `VID_046D&PID_C092` 9 节点 `Status=OK`；G HUB 显示 `G102 LIGHTSYNC` 卡片。
- 厂商通道：探针 `probe_clone_vendor_hid.py --raw` 可收到合法 HID++ 回应，`getFeature` 返回真实 index（0x2201→0x0A、0x8100→0x0F、0x8071→0x0E），非法参数返回错误码 2。

## 已完成项

+ 双板自动角色：运行时 USB 探测 + 对端互补锁定，任意接线顺序、单板复位/断电后自行恢复，身份仅存 RAM。
+ 动态 Profile 与严格克隆：采集真实 Device/Configuration/String/Report Descriptor → 分片 CRC 传输 → P 侧动态构造描述符并重枚举；C092（G102）实机通过，C539（USB Receiver）也曾实机识别并移动（用户确认）。
+ 克隆恢复事务模型（`link_recovery_logic.h`）：请求在途、重复分片/COMMIT 幂等、迟到 ACK 会话绑定、有界重试与共享预算；`PROFILE_ACK` 17 字节携带双方 generation（**两板必须同版本，禁止混刷**）。
+ 控制通道结构性加固：SET 走独立 URB 直连通道，一笔超时不再锁死整条厂商通道；两级自愈 + 预热期豁免。
+ 干扰抑制三件套：克隆完成前抑制纯移动、厂商活动期让路、上电/复位延迟 1 s 启动克隆 USB。
+ 链路层加固：对端静默阈值 750→3000 ms（根除"拆卸风暴"，实测拆卸 58→0 次）、鼠标瞬断 800 ms 防抖、接收溢出不再判故障、自收帧过滤、收发队列各 128 槽。
+ 可观测性：板载滚动日志（上电即记、跨复位续写、跨文件读取、时间戳 `[bN mm:ss.mmm]`、高频行限流、写盘节流）、协议下载通道（UART0 与原生 CDC）、主机 EXE「转存板载日志」、一串统计计数（见 `docs/故障排查总结.md` §5.2）。
+ 输入安全：停止转发/断线/退出路径释放所有按键与鼠标按钮；让路与抑制**只丢纯移动**，带按键报文永不丢。
+ 主机侧产品线（另一条线，近轮未改）：UDP/kmboxNet 远程输入、Lua/宏、日志分类与保留、固件刷写 API、一键发布脚本与 GitHub Actions 发布流程。

## 关键教训与已撤回结论（不要重犯）

- **已撤回/作废**（细节见 `docs/故障排查总结.md`）：移动浅队列（8 槽 + 满则清空）→ 实测丢弃过多、手感明显变差；"移动合并成一条" → 报告率压到约 30 Hz；"同 Profile 沿用现有克隆" → 按要求必须完整卸载+重装；"主机 EXE 用 DTR/RTS 复位板子" → 代码级否证；"板载写盘饿死控制传输" → A/B 否证；"移动是超时主因""移动占满 IO" → 受控 A/B 否证；"固件合成 HID++ 回复" → 实为我 function 位写错；探针"OUT 端点永久阻塞" → 阻塞 I/O 造成的假象。
- **下结论前先自证测量手段**：让路判据三次空转、预热期打点漏赋值（日志里超时值仍写 800 ms 才暴露）、`ctypes` 未声明 `restype` 截断 64 位句柄、用中文过滤乱码控制台输出——都因此返工。
- **警惕死代码**：`on_mouse_report` 这类"永不被调用"的回调曾让一个机制长期空转；给机制加**可观测计数**是发现空转的唯一可靠办法。
- **区分"板子卡"与"设备没答"**：看超时窗口内 1 Hz 统计与链路统计是否照常输出。
- **区分"拥堵"与"个别失败"**：看成功那批的耗时分布（`ctrl_lat_max_us`/`slow10`），而不是只看失败计数。
- **同一时间窗口内的相关性不是因果**：必须用受控 A/B（移动/超时曾同处一个窗口而误导判断）。
- **批量文本删除后立刻编译验证**，不能只看 grep 结果（撤除"同 Profile 沿用"时曾误删相邻代码块）。
