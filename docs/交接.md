## 2026-09-25 **"移动把 IO 占满"被实测否证；去掉"恢复风暴"后 8/9 次干净**

  | 9 | 8 | 1 | 1 |

## 2026-09-25 **触发现象定量：复现率约 1/6；让路机制终于生效但不是超时主因；超时区分预热期**

+ **让路机制：长期空转 → 本轮修好（有计数为证）**
  - 原来写在 `on_mouse_report`（物理路径**不会调用**的回调）里，等于没生效；
  - 搬到真入口 `raw_report_task` 后，**前两次判据仍空转**：① 按"控制任务处理节奏"判 → 超时期间每次处理要等 800 ms，节奏永远稀疏，`vendor_motion=0`；② 改按"到达节奏 + 5 ms 阈值"判 → 实测 **M 侧厂商请求最小到达间隔是 9.4 ms**（`vmin_gap_us=9410`，P 的转发把它整形成约 106 次/秒），5 ms 阈值永不成立，仍为 0；③ 改为**"最近 30 ms 内有厂商请求"**才真正生效：`vendor_motion` = 3635 / 2544。
  - **重要负面结论**：让路生效后超时并未减少（`vendor_motion=2544` 时仍有 6 次超时）→ **"移动是超时主因"这一假设不被支持**（早先的相关性多半来自"两件事都发生在建立窗口内"）。
+ **超时区分预热期（新增）**：实测超时次数随单次等待单调下降（600 ms→8~13、800 ms→18、2500 ms→3），指向"设备枚举后首批应答本身就慢"。故枚举后 10 s 内用 2500 ms、之后用 800 ms（`VENDOR_URB_WARMUP_*`，`s_mouse_ready_us` 打点在鼠标接口注册处）。
  - **过程教训（自造缺陷）**："枚举时刻打点"那次替换**没匹配成功**，而我只核对了变量声明与使用、没核对赋值 → 预热期形同不存在（日志里超时全写 800 ms）。第二次统计时靠"日志里的等待值"才发现。
+ **当前判定**：三个机制里，①克隆前抑制一直有效；②厂商让路本轮才真正生效但**不解决超时**；③预热期已正确生效，但**仍会在复现时出现超时**（含预热期内的 2500 ms 超时）→ 设备侧的偶发不完成仍是主因，我们只能"尽快发现 + 自动恢复"。

## 2026-09-25 **自愈实现并真机验证通过：控制传输卡死可自动恢复，不再需要手动拔插鼠标**

+ **背景（决定性证据，本轮拿到）**：一次控制传输 5 秒未完成（`hid_control_transfer(1034): Control transfer timeout`）后，那一笔传输对象仍"在飞"，后续所有提交被 USB 主机栈以 `ESP_ERR_NOT_FINISHED` 拒绝（源头：`usb_host.c:2016` `HOST_CHECK(!urb_obj->usb_host_inflight, …)`，第三方组件 `espressif/usb 1.5.0`，未纳入 git）。整条厂商通道就此瘫痪 → G HUB 收到不到 HID++ 回应 → **设备在但不识别**；此前只能靠手动拔插鼠标/复位板子恢复。
+ **关键判定（这次现场是控制台采集，1 Hz 统计不节流）**：超时那 5 秒里 **板子照常输出 1 Hz 统计与链路统计** → 开发板完全正常，**是设备未完成该笔传输**；随后失效的是**我们这边的在飞对象**。因此：设备侧成因我们改不了，但"通道永久瘫痪"这一层**属于我们，可以修**。
+ **实现（`firmware/dual_proxy/main/hid_host_mouse.c`）**：
  1. **一级：失败重试**（SET_REPORT 最多重试 2 次，间隔 3 ms）→ `ctrl_retry`；
  2. **一级：重挂接口**（连续失败 ≥5 次 → `hid_host_device_stop` + `start` 每个活动接口，中止在飞传输）→ `recover`；
  3. **二级：根端口断电重枚举**（一级若因在飞传输被挡（`start` 返回 `ESP_ERR_NOT_FINISHED`）→ `usb_host_lib_set_root_port_power(false/true)`，断电 300 ms，等价于拔插一次 USB）→ `port_cycle`；
  4. 统计行新增 `ctrl_retry=` / `recover=` / `port_cycle=`。

## 2026-09-25 **根因确定：链路误判导致克隆被反复拆卸重建**

### 症状与真因

用户报告"延迟接近 1 秒、按键时接近 2 秒"。**实测证明这不是排队延迟，而是输入断流**：

- 主机侧连续移动采样（35 秒窗口，采样自检 38 万 Hz）：`p50=1.19 ms`（稳态本身很快），但出现 **5923 / 2933 / 2727 / 2214 / 1489 / 1389 / 1358 / 1174 ms** 等空档，≥20 ms 空档合计 **28.5 秒 / 35 秒**。
- P 板板载日志（boot b118 内）：**`Profile已配置并挂载` 12 次**（间隔 9~21 秒）、**`开始P侧清理屏障` 58 次**（≈每 3.6 秒一次拆卸）、`UART1对端超时` 15 次、`物理鼠标不可用` 40 次。

**机理（逐行证据，`churn-P.log`）**：
```
W dual_uart1: UART1对端超时，清理实体输入
W dual_uart1: 恢复事务[peer_timeout] role=1 gen=… peer_gen=…
W dual_proxy: 物理鼠标不可用，断开接收端USB：板间UART超时或故障
W dual_pc_hid: 排队P侧清理屏障 → 拆卸克隆（随后重新协商并重装，1~2 秒无输入）
```

**即：鼠标侧板只要静默超过 `LINK_TIMEOUT_MS`（原 750 ms），电脑侧板就判定链路故障 → 拆掉克隆 → 再重装。每次循环 = 1~2 秒输入中断，用户感知为"延迟 1~2 秒、按键更明显"。**这也解释了为何板内队列计数（M `raw_lat_peak_us`≈4.3 ms、P `motion_lat_peak_us`≈4.8 ms）一直很小：报文不是排队，是设备正在消失。

+ **本轮修复（待验证）**：
  1. `uart1_link.c`：`LINK_TIMEOUT_MS` **750 → 3000 ms**（空闲心跳 250 ms，原阈值仅容 3 个心跳周期，误判率过高）；
  2. 新增 M 侧 `hb_gap_peak_ms`（心跳间隔峰值）——用来区分"链路真断"与"本侧任务被饿住"，输出在 UART1 统计行。
+ **验收指标**：修复后 P 板 `开始P侧清理屏障` 与 `已配置并挂载` 的频次应从"每 3.6 秒 / 每 10 秒"降到接近 0（仅在真正拔插时发生）。
+ 相关旁证：P 板曾两次 `reset_reason=1`（掉电复位，非崩溃/看门狗），且 P 的调试口三次整体消失——两者都指向 **P 的 USB/供电线接触不良**（同一根线既供数据又供电）；用户已确认两板电源互不影响。

+ **修复（移动可丢、握手不可丢）**：
  - 消费端：**移动报文不再等待**——克隆未就绪立即丢弃（`motion_only` 判定：鼠标接口 + 匹配鼠标布局 + 按键字节为 0）；厂商报文照旧最长等 5 s。

  - 握手保护窗：克隆挂载后 **2.5 s**（`CLONE_HANDSHAKE_GRACE_US`）内、以及**厂商请求在途 400 ms** 内（`VENDOR_BUSY_WINDOW_US`，GET/SET 回调打时间戳），移动报文直接让路。
  - 安全性：**带按键的报文永不因此丢弃**（按键字节非 0 即不视为纯移动）。
  - 可观测：`HID统计` 新增 `motion_skipped=`（被让路的移动条数）。
+ **真机验证**：复位电脑侧板触发完整重连，同时持续快速移动鼠标——M 板 `reports +31872`、P 板板间 `rx +32671`（移动贯穿整个握手窗口），结果：`角色锁定→request_accepted`(4.3 s) → `Profile提议已接收` + 清理屏障一次成功(4.6 s) → `TinyUSB Driver installed`(4.9 s) → `Profile已配置并挂载 transfer=3 crc=1019ACB2`(5.2 s)；`request_give_up`/`request_no_offer`/`清理失败`/`接收缓冲溢出`/栈溢出 **全 0**；PdP 9 个克隆节点；G HUB 显示 `G102 LIGHTSYNC`。证据：`artifacts/tests/dual-serial-{M,P}-20260925-054046-handshake.log`、`ghub-after-handshake-fix-20260925.png`。
