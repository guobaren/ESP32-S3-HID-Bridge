# 双板识别与实时数据流

## 物理拓扑与证据层级

H 是物理鼠标，M 是 USB Host 板，P 是接电脑的 USB Device 板。线路是 `H ⇄ USB ⇄ M ⇄ UART1 ⇄ P ⇄ USB ⇄ 电脑/G HUB`；P 与 H 没有独立直连线。M/P 的 CH340 UART0 是诊断与软件输入入口，板间 UART1 是另一条 921600 baud 链路。

本项目可观察的是 ESP-IDF Host 和 TinyUSB 交给固件的描述符、HID/控制回调、UART1 帧、队列与 USB 提交/完成回调。它们是**应用/传输层证据**。USB 控制器内部的 ACK/NAK、CRC 错包和总线重试没有进入这些回调；不用外部分析仪不能称作全量 USB 总线抓包。P 的 `tud_hid_n_report()` 返回真只说明 TinyUSB 接受提交，完成回调说明 P 的 USB 传输完成，G HUB 是否解析并接受还要看 G HUB 与后续厂商交互。

```mermaid
flowchart LR
    H[H 物理鼠标] -->|USB 描述符、HID 输入与控制响应| M[M USB Host]
    M -->|UART1 Profile、RAW_HID_INPUT、控制响应| P[P USB Device]
    P -->|克隆描述符、HID 输入| PC[电脑 / G HUB]
    PC -->|HID SET/GET_REPORT| P
    P -->|UART1 控制请求| M
    M -->|USB 控制请求| H
```

## 从插入鼠标到 G HUB 识别

1. **M 枚举 H。** ESP-IDF USB Host 先枚举设备；项目的 `hid_host_mouse.c` 采集原始 Device、Configuration、String、各 HID Report Descriptor，组成 `hid_device_profile_t`。VID/PID、字符串和接口/Report ID/Usage 布局都来自这份 Profile；数据不完整时不得把通用鼠标伪装成物理型号。USB HID 描述符本身就是主机理解 Input/Output/Feature 报告布局的依据，见 [USB-IF HID 规范入口](https://www.usb.org/hid)。
2. **M/P 完成清理与 Profile 事务。** P 先清旧克隆及厂商会话，再发 `PROFILE_REQUEST`；M 重新读取并发 `PROFILE_OFFER`；P 的清理完成 ACK 到达后 M 才发 BEGIN/CHUNK/COMMIT。P 校验长度与 CRC、反序列化、卸载旧 USB 实例、装入新描述符、等待挂载，最后回带双方 generation 的 PROFILE_ACK。细节见 `docs/protocol.md` 的双板流与 `docs/连接流程.md`。
3. **Windows 根据 P 给出的描述符枚举 HID。** P 的 `pc_hid_output.c` 将物理 Device/Configuration/Report Descriptor 构造成 TinyUSB 克隆。Windows 能看到 VID/PID 与 HID 集合只证明枚举层完成；G HUB 卡片出现还依赖后续厂商协议。
4. **G HUB 进行设备特征探测。** 公开的 Logitech [HID++ 2.0 说明](https://github.com/Logitech/cpg-docs/blob/master/hidpp20/README.rst)定义了短报文 `0x10`（7 字节）、长报文 `0x11`（20 字节），字段为 Report ID、Device Index、Feature Index、Function/Software ID、参数。HID++ 2.0 的 Root/GetFeature 将 Feature ID 映射到该设备本次会话的 Feature Index；不能把某型号观察到的 index 写死成所有设备通用值。项目实测 C092 对 `0x2201` DPI、`0x8100` 板载配置、`0x8071` 灯效的 getFeature 返回了设备真实 index；这只是该样本的观察，不是 G HUB 私有识别算法的完整公开描述。
5. **厂商请求穿过两板。** 电脑发给 P 的 HID GET_REPORT/SET_REPORT 在 `pc_hid_output.c` 回调中转成带 transaction ID、interface、Report ID/type 的 UART1 消息。M 的 `hid_host_mouse.c` 对 H 执行物理控制传输；SET_REPORT 需在发向 H 前恢复 TinyUSB 已剥离的 Report ID，GET_REPORT 返回时要去掉重复 ID。P 按事务与当前 vendor session 校验响应，再交还 USB 回调。H 的 vendor HID 中断输入同样由 M 原样转发到 P，再送给电脑。超时、队列拒绝、会话切换都可能使单笔交互失败，G HUB 因而可能显示灰卡。

**边界：** P 的设备级 `tud_vendor_control_xfer_cb` 目前仅记录 SETUP 并返回 STALL；这类非 HID class 的 vendor EP0 请求尚未跨板转发。不能因为记录到了请求就称“厂商所有请求均得到正确响应”。当前串口接口能保存回调可见的请求与结果，并允许注入受支持的 HID 消息用于实验；对未知命令返回固定成功会伪造识别结果，因此没有这样做。

## 物理鼠标移动时的逐站信息

1. H 的传感器更新位移；USB Host 按中断端点轮询，M 收到带 Report ID/接口身份的原始 HID Input 报告。M 的 USB callback 把报告放入 `HID_REPORT` 队列。鼠标 X/Y、按钮、滚轮的位/字节位置必须按实际 Report Descriptor 解析，不能假定所有鼠标同布局。
2. M 的 `raw_report_task` 在克隆未就绪或厂商事务密集期可**只让纯移动**让路；带按键的报告继续转发。被让路的报告应出现在 M 端原始输入事件，但不会出现对应的 UART1 TX。当前主路径发 `RAW_HID_INPUT(0x27)`，携带 interface、Report ID 和原始报告；不能把历史遗留的 `on_mouse_report` 回调当作当前物理移动来源。
3. M UART1 发送队列与驱动把帧写出；P UART1 验证角色、generation、序号和 CRC 后交给 `dual_proxy_app.c`。P 的 `pc_hid_output.c` 按 Profile 布局判断是否为纯移动，分别放入移动/厂商输入队列；握手窗口可能再次抑制纯移动。
4. P 发送任务检查克隆/端点状态，调用 `tud_hid_n_report()` 提交 USB HID Input 报告；随后报告完成或失败回调给出更靠后的证据。Windows 鼠标栈再转换为指针或按钮行为。显示指针位移还受到电脑端指针设置与目标窗口消费影响，板端无法直接回读。

## 通过 M UART0 注入移动的诊断路线

`--inject-move 20 0` 发 `SESSION_START`、7 字节 `MOUSE_REPORT{buttons=0,x=20,y=0,wheel=0,pan=0}`，随后发 `RELEASE_ALL`。这条**软件输入**路径在 M 通过 `SOFTWARE_MOUSE(0x2B)` 进入 UART1；P 可直接入软件平滑器（该命令的平滑槽为 0），最终从 USB HID 提交。它与 H 的 `RAW_HID_INPUT` 路径在 M 的入口不同，之后共享 UART1/P USB 的关键通路。即使 H 不在位也允许尝试注入，后续克隆门控会如实决定是否能送达。

实时视图按顺序寻找：M UART0 RX → M UART1 TX → P UART1 RX → P USB SUBMIT → P USB COMPLETE。前三站可按 7 字节载荷匹配；P USB 阶段目前按时间窗关联，因为板间帧没有统一 trace ID，物理鼠标同时移动会造成歧义。建议注入时静止 H，并核对各队列 `rejected/dropped` 与诊断流 `dropped` 没有增长。任何一站缺失、时间窗混杂或计数增长，都应判为这次实测**未确认完整通路**。

## 串口操作与注入边界

先运行 `python tools/dual_uart_inspect.py --ports COMx,COMy --seconds 60`。工具使用 nonce 匹配 `DEVICE_HELLO`，自动标 M/P；启动时下载板载日志尾部恢复最近 Profile/克隆摘要，然后订阅实时事件。每端保存 UART0 原始 RX/TX、JSONL 事件和摘要。需要备份鼠标信息时使用 `--save-profile mouse.hidp`；向 P 手动安装时使用 `--inject-profile mouse.hidp`。手动 Profile 可覆盖在线会话，P 暂停处理 M 会话；`--restore-auto-profile` 清理手动克隆并重新申请真实 Profile。

`--inject-frame p TYPE HEX` 把已编码的 `RAW_HID_INPUT` 或 `HID_GET_REPORT_RESPONSE` 送入 P 的接收处理函数；`--inject-frame m TYPE HEX` 把已编码的 `HID_SET_REPORT` 或 `HID_GET_REPORT_REQUEST` 送入 M 的物理鼠标控制队列。返回 0 只表示函数已收到完整解码载荷，后续队列入队、物理控制传输与 USB 完成要看实时事件和统计。该接口不接受任意 USB SETUP 包、不能绕过物理控制器驱动直接注入总线握手，也没有自动构造 HID++ 应答表。

串口打开本身可能触发 CH340 DTR/RTS 线态变化；工具设置 DTR/RTS 为低，但不能把“打开过串口”当作完全无扰动采集。当前固件修改在完成双板同版本刷写及真实串口验收前，不应把上述路径标为真机通过。
