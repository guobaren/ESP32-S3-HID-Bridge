# 双板桥接故障排查总结：猜测、验证与修复

> 本文档记录本阶段（"接完 P 再插 H 时快速移动鼠标 → 驱动不识别/设备卡死"）排查过程中的**每一条猜测、验证方法、实测证据、结论（成立/否证）与对应修复**。
> 原则：**只有实测数据支持的结论才写"成立"**；被否证的猜测一并保留（避免后人重走弯路）；未验证的一律标注"未验证"。
> 详细时间线见 `docs/交接.md`，质量与风险清单见 `docs/审计.md`。

## 一、现象与影响

| 项 | 内容 |
|---|---|
| 现象 | 电脑侧 G HUB 显示「连接 Logitech 装备 / 恢复设备 / 正在设置…」（灰卡），设备在但不被识别；严重时鼠标完全不动 |
| 触发 | 先接好 P（电脑侧板），再插入 H（鼠标）时**快速移动鼠标**；或复位 M 后立刻快速移动 |
| 复现率 | 实测 **约 10%/次复位**（早期两轮为 1/6 与 1/9，间歇性、非必现） |
| 影响面 | 仅"克隆/厂商通道"异常；稳态移动与控制传输本身无性能退化（见 §4.6） |
| 当前状态 | 已能**自动恢复**（无需拔插鼠标）；**设备侧偶发不完成控制传输的成因仍未定**（见 §6） |

## 四、成立的关键机制与修复

### 4.1 G6：对端静默阈值过紧 → 克隆反复拆装（churn）

- **机制**：M 每 250 ms 发一次心跳（`DUAL_MESSAGE_LINK_PING`），P 侧 `LINK_TIMEOUT_MS` 原为 **750 ms**；实测 M 心跳间隔**峰值 737 ms**（`hb_gap_peak_ms`），仅 13 ms 余量 → 偶发误判"对端掉线" → 拆卸克隆并重装。
- **实测**：约 210 秒窗口内 **清理 58 次 / 挂载 12 次**；用户体感"每 10~20 秒卡 1~2 秒，点击时更严重"。
- **修复**：`LINK_TIMEOUT_MS 750 → 3000`（`firmware/dual_proxy/main/uart1_link.c`）。
- **验证**：改后 150 秒窗口 `开始P侧清理屏障=0`、`已配置并挂载=0`、`UART1对端超时=0`；后续多轮长窗口均 **拆卸 0 次**。

### 4.2 G9：控制传输"在飞对象"导致通道永久锁死（根因）

- **机制（第三方源码级）**：
  - `usb_host_hid` 组件整个设备只用**一个** `usb_transfer_t`（`hid_host.c:85 ctrl_xfer`）；
  - 提交时 `usb_host_transfer_submit_control()` 先做 `HOST_CHECK(!urb_obj->usb_host_inflight, ESP_ERR_NOT_FINISHED)`（`usb/src/usb_host.c`，本版本 2027 行）；
  - 该栈的**逐传输超时未实现**：`usb_types_stack.h:171` 注释明写 *currently not supported yet*；
  - 组件的 5 秒只是**软件等待**（`hid_host.c:75 DEFAULT_TIMEOUT_MS=5000`，等待信号量），**超时后不取消、不释放**那笔 URB。
- **后果**：一次超时 → URB 仍在飞 → 后续每次提交都被 `ESP_ERR_NOT_FINISHED` 拒绝 → **整条 HID++（厂商）通道瘫痪**；因为对象是**按设备**共享的，鼠标接口与厂商接口一起废 → G HUB 收不到任何回应 → 灰卡。
- **日志实证**：`hid_control_transfer(1034): Control transfer timeout` → `result=ESP_ERR_TIMEOUT` → `hid_control_transfer(1028): Unable to submit control transfer` → `result=ESP_ERR_NOT_FINISHED`（连续多次）。
- **修复（结构性）**：新增 `firmware/dual_proxy/main/vendor_urb.{c,h}`——**每个请求独立分配 URB**（`usb_host_transfer_alloc`），完成后立即释放；`hid_host_mouse.c` 的 SET 路径经编译开关 `VENDOR_USE_DIRECT_URB` 切到该通道（可一键回退）。
- **验证**：初始化突发 `urb_sub=168 urb_ok=168 urb_to=0`；触发场景下即使出现超时，**通道不再锁死**（`urb_ok` 持续推进）。

### 4.3 恢复策略（两级 + 预热期豁免）

| 级别 | 触发 | 动作 | 验证 |
|---|---|---|---|
| 重试 | 单次失败 | 用**新的独立 URB** 再发一次（`urb_retry`） | 瞬时抖动被吃掉 |
| 一级 | 连续 3 次请求失败且非预热期 | 对每个活动接口 `hid_host_device_stop` + `start`（尝试中止在飞传输） | 实测 `stop=ESP_OK start=ESP_OK` |
| 二级 | 一级的 `start` 失败（仍被在飞挡住） | **根端口断电重枚举**（`usb_host_lib_set_root_port_power(false/true)`，断 300 ms） | 实测 `power off=ESP_OK on=ESP_OK` → 设备重新枚举（addr 1→2）→ 克隆重建（`收到Profile ACK：transfer=2`） |

- **为什么用"端口断电"而不是 abort**：本版本公开 API **没有** `usb_host_transfer_abort`；且实测 `usb_host_endpoint_flush(dev, 0)` 返回 `ESP_ERR_INVALID_ARG`（EP0 不可寻址）。因此超时的 URB 只能**挂为孤儿**（标记 `orphan`，由回调在它最终完成时释放），并靠端口断电来强制中止。
- **G13 修复**：预热期（枚举后 10 秒）内**只重试+计数、不升级**——否则"端口断电 → 重新枚举 → 设备再进慢阶段"会形成恢复风暴（实测一个窗口 `port_cycle=2`、超时 12 次）。改后连续 8 次复位中 **8/9 次完全干净**。

### 4.4 G7：鼠标瞬断防抖

- `MOUSE_GONE_DEBOUNCE_US 800000`：设备消失先挂起，800 ms 内若 `HID_EVENT_CONNECTED` 回来则取消（避免一次瞬断触发"拆卸+重装"）。

### 4.5 G8：优先级重排（避免初始化被移动流量挤掉）

- M 侧：`hid_control_worker 5→7`、`hid_host_events 4→5`、`usb_host_events 3→4`、`usb_desc_client 2→6`、`hid_profile_publish 2→6`，`raw_report_task` 保持 6，统计任务最低（2）。
- 效果：厂商控制不再被 1 kHz 移动抢占；G HUB 初始化序列不再中途中断。
- 遗留：P 侧仍是 `sender=8 > vendor_input=7 > vendor_control=6`（未改，实测未暴露问题，已记入风险）。

### 4.6 G11：**"移动占满 IO"被直接否证**（本轮最重要的否证）

- **方法**：同一探针压力（HID++ 查询经克隆转发到物理设备），比较"静止"与"快速移动"。
- **数据（真实设备）**：

  | 组 | 移动报文 | 控制传输 | 失败 | 最慢耗时 | >10 ms | >100 ms |
  |---|---:|---:|---:|---:|---:|---:|
  | A 静止 | 0（确认静止） | 388 | **0** | 9 ms | 0 | 0 |
  | B 快速移动 | **58146（≈1.1 kHz 持续）** | 388 | **0** | **9 ms（完全未变）** | **0** | **0** |

- **结论**：稳态下移动**完全不影响**控制传输；"IO 被占满"不成立。
- **自我纠正**：此前我曾用"让路生效但超时没减少"去否证"移动是主因"，**那一步推理不成立**——让路是在 M **已收到**报文之后才丢弃的，从不减少 USB 侧负载。本次 A/B 才是直接证据。

### 4.7 G12：克隆期间的干扰抑制（有效，但有边界）

| 机制 | 实现位置 | 实测 |
|---|---|---|
| 克隆完成前不转发纯移动 | `raw_report_task`（`!dual_uart1_clone_ready()`） | 每次实测拦下 **972 / 995 / 1177 / 1343** 条 |
| 厂商活动期让路 | `raw_report_task`（`dual_hid_host_vendor_busy()`） | `vendor_motion` = 3635 / 2544 |
| 上电/复位后延迟 1 秒再启动克隆相关 USB | `dual_proxy_app.c: wait_clone_usb_start_delay()` | 日志 `上电/复位延迟：先等 1000 ms` → `+1032 ms` 启动探测栈 |

- **让路机制的曲折（三次才生效，值得记录）**：
  1. 原实现写在 `on_mouse_report` —— 该回调在**物理报文路径上根本不会被调用**（死代码）→ 长期空转；
  2. 搬到真入口后按"控制任务**处理**节奏"判突发 —— 超时期间每次处理要等 800 ms，节奏永远稀疏 → `vendor_motion=0`；
  3. 改按"**到达**节奏 + 5 ms 阈值" —— 实测 M 侧厂商请求**最小到达间隔 9.4 ms**（`vmin_gap_us=9410`，P 的转发把它整形成约 106 次/秒），5 ms 永不成立 → 仍为 0；
  4. 最终按"**最近 30 ms 内有厂商请求**"判定 → 真正生效。
- **边界**：让路生效**并未减少超时**（`vendor_motion=2544` 的一次仍有 6 次超时）→ 该机制的价值是"克隆建立期不被移动干扰"，而非解决超时。

## 五、当前架构与可观测计数（排查速查）

### 5.1 数据通路

```
物理鼠标 --USB--> M(USB Host, 中断IN) --UART1--> P --克隆(中断IN)--> 电脑
                      |                                  ^
                      +-- EP0 控制传输（转发 G HUB 的 HID++）--+
                          （SET 走 vendor_urb 直连通道；GET 仍走组件路径）
```

### 5.2 统计行字段（`Host HID统计`，每秒/每 10 秒一条）

| 字段 | 含义 | 异常判读 |
|---|---|---|
| `reports` | 从物理鼠标收到的报文数 | 不增长且你在移动 → 设备侧输入停了 |
| `wheel` | 其中滚轮报文数 | 同上（专门验证滚轮） |
| `vendor_reports` | 厂商接口输入报文数 | 冻结 → HID++ 无来往 |
| `control` / `control_fail` | 控制传输请求数 / 失败数 | `fail` 持续增长 → 通道异常 |
| `urb_sub/urb_ok/urb_to/urb_retry` | 直连通道：提交 / 成功 / 超时 / 重发 | `to` 增长但 `ok` 仍增长 → 通道未锁死 |
| `ctrl_lat_max_us` / `slow10` / `slow100` | 成功传输耗时峰值 / >10 ms / >100 ms 笔数 | 峰值与慢笔数显著上升 → 拥堵；否则为"个别整笔失败" |
| `recover` / `port_cycle` | 一级重挂次数 / 端口断电次数 | 频繁 → 设备侧反复异常 |
| `preclone_motion` / `vendor_motion` | 克隆前抑制 / 厂商活动期让路条数 | 值为 0 需怀疑判据是否生效（曾空转三次） |
| `vmin_gap_us` | 厂商请求到达最小间隔 | 判据调参依据（实测 9.4 ms） |
| `hb_gap_peak_ms`（UART1 统计行） | 心跳间隔峰值 | 接近对端静默阈值 → 需调大阈值 |

### 5.3 复现与取证方法

1. 确认端口（M 板串口编号会变）：`[System.IO.Ports.SerialPort]::GetPortNames()`；
2. 采集：`python tools/capture_dual_serial.py --ports COM13 --labels M --seconds 200 --reset-port COM13 --reset-after 2 --tag <标记>`；
3. 复现：复位后**立刻持续移动鼠标**约 20 秒（可重复多次）；
4. 关键行：`上电/复位延迟`（复位确认）、`控制传输超时（N ms）`（含等待值，可判定预热期是否生效）、`自动恢复第 N 次`、`二级恢复第 N 次`、`根端口 power`、`收到Profile ACK`（克隆重建）。

## 七、验证方法学（本轮教训，供后续沿用）

1. **先量后改**：所有"成立"的结论都有计数或日志支撑；被否证的猜测也记录在案。
2. **下结论前先自证测量手段**：本轮多次因"未核对生效证据"返工——让路判据三次空转、预热期打点漏赋值（日志里超时值仍写 800 ms 才暴露）、`ctypes` 未声明 `restype` 导致 64 位句柄截断、用中文过滤乱码控制台输出。
3. **区分"板子卡"与"设备没答"**：用"超时窗口内 1 Hz 统计是否照常"这一条即可分开，比猜测可靠。
4. **区分"拥堵"与"个别失败"**：看**成功那批的耗时分布**（`ctrl_lat_max_us`/`slow10`），而不是只看失败计数。
5. **注意"看似相关"**：移动与超时同处一个时间窗口，容易误判因果——必须用受控 A/B。
6. **警惕死代码**：`on_mouse_report` 一类"永远不会被调用"的回调曾让一个机制空转很久；给机制加**可观测计数**是发现空转的唯一可靠办法。
