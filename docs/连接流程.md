# 双 ESP32-S3 HID Bridge 完整连接流程

本文描述当前 `firmware/dual_proxy` 固件的连接流程和已知缺口；待实施的目标见[连接恢复修复方案](连接恢复修复方案.md)，验收场景见[双板连接恢复矩阵](双板连接恢复矩阵.md)。代码路径不代表实机通过。默认拓扑如下：

```text
控制电脑 A ── UART0/USB-C ── 鼠标侧板 M ── USB Host ── 物理鼠标
                                      │ UART1 GPIO17/18/GND
被控电脑 B ── USB Device ─────────────┘
                         电脑侧板 P
```

两块板使用相同固件，但运行时根据 USB 连接证据和 UART1 对端身份锁定不同角色：

- `MOUSE_HOST=2`：连接物理鼠标，负责 USB Host 枚举、读取 HID、采集 Profile、转发实体输入和接收控制电脑的软件输入。
- `PC_DEVICE=1`：连接被控电脑，负责按 Profile 动态创建 USB HID 克隆设备、接收实体/软件输入并提交给被控电脑，同时透传厂商 HID 控制请求。

## 1. 上电初始化

每块板复位后都从 RAM 空状态开始，不保存上一次角色。应用执行以下步骤：

1. 读取 ESP32-S3 MAC 作为 `node_id`。
2. 初始化状态 LED。
3. 启动 UART1：
   - TX=`GPIO17`，RX=`GPIO18`；必须交叉连接：M.TX→P.RX、M.RX→P.TX，并共地。
   - 波特率 `921600`。
   - RX 缓冲区 4096 字节，普通发送队列 64 项，安全队列 8 项，软件输入队列 32 项，厂商控制队列 32 项。
   - UART1 帧带类型、长度、序号和 CRC；序号重复或回退的帧会被丢弃。
4. UART1 初始角色为 `UNRESOLVED=0`，USB 状态为 `WAITING=0`，生成本次启动唯一的非零 `generation:u32`。
5. 首先启动 USB Device 探测窗口，窗口长度 3 秒；若没有电脑连接，再停止 Device 探测并切换 Host 探测窗口。未确定身份时每 3 秒轮换一次。
6. 未确定身份时 LED 熄灭；身份已确定但对端未连接时红色常亮；对端在线后 `MOUSE_HOST` 绿色、`PC_DEVICE` 蓝色。

## 2. 身份确定

### 2.1 UART1 身份广播

UART1 周期性发送：

```text
LINK_HELLO (0x20), 12 bytes
  role:u8          0=UNRESOLVED, 1=PC_DEVICE, 2=MOUSE_HOST
  usb_state:u8     0=WAITING, 1=MOUNTED, 2=HID_CONNECTED,
                   3=DISCONNECTED, 4=ERROR
  node_id[6]
  generation:u32

LINK_PING (0x23), 4 bytes
  generation:u32
```

当前状态广播周期约为 250 ms；UART1 超过 750 ms 没有收到对端活动即视为链路故障。

### 2.2 有一侧先确认身份

- 如果某板在 Device 探测中检测到 USB 主机连接（`usb_attached` 或 `tud_mounted()`），它锁定为 `PC_DEVICE`。
- 如果某板在 Host 探测中检测到 USB 鼠标/接收器设备，它锁定为 `MOUSE_HOST`。
- 如果先收到对端的确定身份，则本板直接锁定为互补角色；例如收到 `peer=MOUSE_HOST`，本板锁定 `PC_DEVICE`。
- 当前假设拓扑合法：两板身份必然不同，且一板接电脑、一板接鼠标；没有增加同角色仲裁机制。

角色锁定后本次上电不再因 USB 暂时拔出或 UART 短时断开而重新选角色。只有重新上电/复位，才会回到 `UNRESOLVED`。

### 2.3 身份确认回传

双方收到已确定的 `LINK_HELLO` 后回传：

```text
ROLE_ACK (0x2F), 5 bytes
  acknowledged_role:u8
  generation:u32
```

`ROLE_ACK` 只确认对端身份声明已被接受，不代表 USB HID 已经挂载。

## 3. PC_DEVICE（电脑侧板 P）启动流程

角色锁定后，P 按顺序执行：

1. 清空 Profile 接收器状态。
2. 调用 `dual_pc_hid_prepare_for_profile()`，撤销旧的动态 HID 会话、清理旧描述符和输入状态。
3. 启用动态重配置任务。
4. 将 UART1 本机状态设为 `WAITING`，广播 `LINK_HELLO(role=PC_DEVICE)`。
5. 开放 Profile 请求门控并等待物理 Profile；当前没有新克隆挂载，实际 TinyUSB 克隆安装发生在完整 Profile 到达之后。
6. P 身份确定、M 在线且当前身份获得 `ROLE_ACK` 后，对该 M 会话发送一次 `PROFILE_REQUEST`，请求 M 重新获取当前 USB 信息；M 未在线则 P 红色常亮等待。请求带 P 的 `generation` 与 `flow_id`。当前诊断实现等待 `FLOW_ACK` 最多 5 秒，超时后将本次事务终止为失败；同 generation 的自动恢复能力尚不完整。此参数是当前诊断值，不是已验收的 10 秒恢复参数。待实施修复见[连接恢复修复方案](连接恢复修复方案.md)。

## 4. MOUSE_HOST（鼠标侧板 M）启动流程

角色锁定后，M 按顺序执行：

1. 启动 USB Host HID 栈。
2. 启动 UART0 控制协议，角色字段为 `MOUSE_HOST`，用于控制电脑 A 的软件鼠标命令。
3. 将 UART1 本机状态设为 `WAITING`，广播 `LINK_HELLO(role=MOUSE_HOST)`。
4. USB Host 枚举物理鼠标/无线接收器。枚举到至少一个物理 HID 接口后即可确认 MOUSE_HOST；不要求鼠标布局已经全部解析完成。
5. 读取并缓存物理设备 Profile，包括：USB Device Descriptor、Configuration Descriptor、字符串、各 HID Report Descriptor、接口/端点属性及 CRC32。
6. Profile 采集完成后，若 P 在线，M 发起一次 `PROFILE_OFFER`；P 不在线则 M 红色常亮，保留采集结果等待新会话。P 对 OFFER 完成清理并回 `FLOW_ACK` 后，M 才按 `BEGIN → CHUNK* → COMMIT` 发送。当前诊断实现的 5 秒确认超时会终止本次流程；该参数及失败恢复尚未完成实机验收。待实施修复见[连接恢复修复方案](连接恢复修复方案.md)。

## 5. Profile 传输与动态 USB 克隆

### 5.1 P 请求、M 响应

P 发起时发送：

```text
PROFILE_REQUEST (0x30), 8 bytes
  pc_generation:u32
  flow_id:u32
```

M 接受后回 `FLOW_ACK(PROFILE_REQUEST, flow_id, status, recipient_generation, sender_generation)`，并在发布任务中重新读取当前 USB Device/Configuration 描述符，将仍在线的 Report Descriptor 快照重新序列化。M 自行采集完成时发送 `PROFILE_OFFER(flow_id, transfer_id, crc32)`；P 收到后释放输入并排入清理任务。P 必须先完成 TinyUSB 卸载和旧会话清理，才回 `FLOW_ACK(PROFILE_OFFER, flow_id, status, recipient_generation, sender_generation)`；清理失败不能回成功 ACK。`FLOW_ACK` 当前为 14 字节，包含双方本次启动的 generation（字段定义见 `firmware/dual_proxy/main/bridge_protocol.h:93-103`）。当前接收确认超时为 5 秒诊断值；重试策略仍待实施。

Profile 数据按以下阶段发送：

```text
PROFILE_BEGIN
PROFILE_CHUNK (多个分片)
PROFILE_COMMIT
```

Profile 发送是低优先级流，但实体鼠标报告和安全释放优先于普通 Profile 分片。完整 `COMMIT` 到达后 P 回 `FLOW_ACK(PROFILE_COMMIT, transfer_id, status)`；当前诊断实现超过 5 秒未获确认就将发送标记失败。重复分片、缺片恢复、重复 COMMIT 和最终 ACK 丢失后的补确认尚未完成故障注入验证。连续发送 Profile 分片时，每累计最多 8 个实体运动报告让出一个 Profile 发送机会。

### 5.2 P 接收和 USB 重配置

P 收到完整且 CRC 正确的 Profile 后：

1. 校验 transfer ID、长度、CRC 和各描述符边界。
2. 立即使旧厂商 HID 会话失效。
3. 释放旧输入、使旧厂商队列与异步工作失效，并排队带 epoch 的重配置。
4. worker 撤载旧 TinyUSB Device 实例，执行 USB detach；成功后清空旧 Profile、描述符和 Report 模板，避免旧实例在线时覆写描述符。
5. 等待约 300 ms，使用新 Profile 构造 VID/PID、字符串、Configuration、HID Interface 和 Report Descriptor。
6. 安装新 TinyUSB Device 实例并重新 attach。
7. 仅当 `tud_mounted()` 成功后，P 才认为克隆设备已经挂载。
8. 发送：

```text
PROFILE_ACK (0x2E), 9 bytes
  transfer_id:u32
  crc32:u32
  status:u8    0=成功，1=不可克隆/失败
```

9. 成功后 P 将 UART1 状态改为 `HID_CONNECTED=2`，并保持蓝色 LED；软件输入到达时蓝灯短暂闪烁。

`FLOW_ACK` 只确认对端接收并接受消息，且清理类 ACK 必须晚于 P 的实际清理完成；`PROFILE_ACK` 表示 P 最终完成或拒绝 USB 克隆。P 的安装/挂载失败会红灯闪烁；M 的采集、发送或确认失败也会红灯闪烁。当前实现会在确认超时后终止相应事务；同 generation 的有限重试和恢复路径尚未完成。M 收到匹配成功的 `PROFILE_ACK` 后目前尚未将自己的 UART1 状态更新为 `HID_CONNECTED`，这是待修复项，不应被视为已实现。完整方案见[连接恢复修复方案](连接恢复修复方案.md)。

## 6. 实体鼠标输入路径

物理输入不经过主机软件，不依赖电脑 A 的 EXE：

```text
物理鼠标 USB
  → M 的 USB Host HID 回调
  → 标准化 PHYSICAL_MOUSE (0x21)
  → UART1
  → P 的 PHYSICAL_MOUSE 处理
  → 动态克隆 USB HID IN report
  → 被控电脑 B
```

`PHYSICAL_MOUSE` payload 为 9 字节：

```text
interface:u8, report_id:u8, buttons:u8,
x:i16, y:i16, wheel:i8, pan:i8
```

P 侧实体输入优先于软件输入和 Profile 普通分片。鼠标拔出、UART 故障或停止转发时，必须先发送/执行 `PHYSICAL_RELEASE`，释放所有物理来源按钮。

## 7. 软件鼠标输入路径

控制电脑 A 通过 UART0/USB-C 向 M 发送软件鼠标报告。M 只有在物理鼠标 Host 接口存在时才接受移动命令；释放命令始终放行。

```text
电脑 A EXE
  → M UART0
  → M 校验角色/物理鼠标存在
  → SOFTWARE_MOUSE (0x2B) 经 UART1
  → P 软件输入合并器
  → 5 个滚动 1 ms 槽
  → P 1000 Hz HID 输出任务
  → 被控电脑 B
```

软件输入支持 7/8 字节标准化报告。P 将 X/Y/Wheel/Pan 按整数商和余数分散到 5 个 1 ms 槽，代数严格守恒；实体鼠标报告不进入该平滑器，因此不会被软件平滑队列阻塞。

软件租约超时、UART0 断开、UART1 故障、EXE 退出或队列错误时发送 `SOFTWARE_RELEASE (0x2C)`，P 侧清除软件来源按钮和计划移动。

## 8. 厂商 HID 控制/驱动通信路径

被控电脑 B 的厂商驱动（例如 G HUB）向动态克隆设备发起 HID 控制请求：

```text
电脑 B HID GET/SET_REPORT
  → P TinyUSB Device
  → HID_GET_REPORT_REQUEST / HID_SET_REPORT 经 UART1
  → M USB Host 对物理鼠标执行原始控制请求
  → HID_*_RESPONSE / RAW_HID_INPUT 经 UART1
  → P 返回给电脑 B
```

厂商请求使用独立 vendor 队列；实体运动队列不会被 vendor burst 直接挤掉，发送调度会周期性给 vendor 控制流让出槽位。无法安全解析相对 X/Y、buttons、wheel 或 pan 的设备仍可尝试原始厂商通信，但软件叠加会被禁用。

## 9. 鼠标拔出/插回

### 9.1 只拔出物理鼠标

M 检测到 Host 设备断开后：

1. 将自身 `usb_state` 设为 `DISCONNECTED`，停止新的实体报告。
2. 排队 `PHYSICAL_RELEASE`。
3. 取消旧 Profile 发送和缓存状态，建立带双方 generation 与 event ID 的 GONE 清理屏障。
4. TX 任务在对端在线且身份已确认后发送 `DEVICE_GONE (0x2D)`；屏障期间禁止新 OFFER/传输。

P 收到 `DEVICE_GONE` 后：

1. 释放物理和软件输入。
2. 清空 Profile 接收器，使旧厂商会话和待装 Profile 失效，并排队清理。
3. worker 执行 USB detach；卸载成功后清空旧描述符和克隆状态。
4. 保留角色 `PC_DEVICE`；实际卸载和旧会话清理完成后，才回与该 `event_id` 及双方 generation 匹配的成功 `FLOW_ACK`，随后等待 M 推送新 Profile。

插回鼠标后，M 可先重新枚举并采集新连接的 Profile；旧 `DEVICE_GONE` 清理屏障完成前，不能开始新 OFFER/传输。完成后按新事务安装 Profile。重复/迟到的旧事件不得清理新设备。恢复是否在 10 秒内完成，必须以同步日志、Windows PnP、G HUB 和输入结果实测为准；当前仅普通拔插已有局部历史证据，快速插回与拔出期间复位仍未验证。

### 9.2 只复位鼠标侧板 M

M 的 generation 改变；P 观察到新会话后撤销旧 Profile，并主动发起一次 `PROFILE_REQUEST`。M 重新读取当前物理 USB 信息、发送与该事务匹配的 `PROFILE_OFFER` 并等待 P 完成清理后确认，然后传输 Profile；P 完成重枚举并回最终 ACK。旧会话缓存的 Profile 不得自行发起新会话 OFFER，以免与 P 的请求形成并发克隆。当前同会话失败后的有界重试尚未实施。

### 9.3 只复位电脑侧板 P

P 清空自身 Profile/USB 状态并重新锁定 `PC_DEVICE`。P 在线、身份获确认且完成本地清理后主动发送 `PROFILE_REQUEST`；M 重新读取当前 USB 信息，发布新 Profile 并向 P 发 OFFER。P 先完成 OFFER 清理并回 `FLOW_ACK`，再接收/挂载 Profile，最后发送匹配的 `PROFILE_ACK`。以上为当前正常路径；清理失败重试、确认丢失恢复仍待实施，10 秒恢复时限未验收。

### 9.4 两板同时断电或复位

两板都丢失 RAM 中的角色、序号窗口、Profile ACK 状态和会话状态。上电后重新经历 USB 探测、UART1 HELLO/ROLE_ACK、Profile 请求/采集/重枚举流程。两板必须刷入同一协议版本；混刷旧版本会导致 HELLO/PING/Profile 字段不兼容。

## 10. UART1 故障与安全释放

UART1 超过约 750 ms 无有效帧、CRC/帧错误或协议异常时，按整条代理链路故障处理：

- P：释放所有输入、撤下动态 HID、清空 Profile 接收器，等待对端重新建立会话。
- M：清空厂商控制队列，物理鼠标仍由 USB Host 监视；重新建立会话后由 P 的 REQUEST 触发采集和发布，不能将旧缓存自动重发视为恢复保证。
- 所有停止/断线/退出路径都必须释放物理和软件鼠标按钮、键盘按钮，避免目标电脑出现卡键。

## 11. 状态灯含义

| 灯状态 | 含义 |
|---|---|
| 熄灭 | 尚未确定身份 |
| 红色常亮 | 身份已确定，但板间对端未连接 |
| 红色闪烁 | 本板采集、发送确认或 USB 克隆流程失败 |
| 绿色 | 已锁定 `MOUSE_HOST` 且板间对端在线 |
| 蓝色 | 已锁定 `PC_DEVICE` 且板间对端在线 |
| 蓝灯短闪 | 电脑侧收到/提交软件输入 |

角色颜色绑定角色，不因普通 USB 暂时断开而改变；这便于区分“角色已锁定但设备暂时未连接”和“仍在身份探测”。

## 12. 当前验证边界

- 已有真实证据：动态 Logitech Profile、G HUB 识别、实体移动、软件移动、厂商 HID++ 控制请求和部分单板复位恢复。
- 当前文档描述的是代码路径和协议语义；任意品牌、复杂 Composite/Vendor HID、长时间 1000 Hz、所有线序和所有复位时机仍需逐项实测。
- 静态 Windows PnP 节点只能证明当前枚举存在，不能单独证明 G HUB 驱动识别成功。
- 打开 COM9/COM13 进行日志采集可能通过 DTR/RTS 触发对应板复位，采集结果必须标注这一扰动。
- 当前清理屏障实现仅有构建、纯逻辑测试和刷写证据；双板异步时序、清理失败恢复、迟到/丢失 ACK、快速插回、M/P 单独复位、G HUB 与 10 秒恢复均未验证。详见[待实施的连接恢复修复方案](连接恢复修复方案.md)。
