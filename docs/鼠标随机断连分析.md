# 鼠标随机断连（USB Host 冻结）分析与处置

> 本文汇总 2026-09-27 ~ 09-28 两天的真机观测、排除性实验、当前自愈方案与上游信息。
> 当前证据将断点定位在 M 板与物理鼠标之间的 USB Host 路径；它与 ESP-IDF
> [issue #14996](https://github.com/espressif/esp-idf/issues/14996) 的症状相似，
> 但尚无总线证据证明根因相同。文中约 4~7 秒的自动恢复成绩属于旧版端口断电方案；
> 当前无 reset 固件默认不再执行该动作，完整 USB Host 冻结后的恢复能力未验证。

---

## 1. 现象

**用户可感知的症状**：鼠标突然不动（严重时键盘也无响应），板子其他功能看起来正常；
等待若干秒后"自己好了"（用户原话：*"卡了十几秒后自己好了"*）。

**实测出现次数（2026-09-27 ~ 09-28，共 9 次事件）**：

| 时刻 | 类型 | 检测延迟 | 总中断 |
|---|---|---|---|
| 01:08:57 | 物理拔出（人工插拔） | — | 45.42 s |
| 03:01:33 | **冻结** | 4441 ms | 7.56 s |
| 03:07:56 | **冻结** | 10950 ms | 14.05 s |
| 04:28:04 | **冻结** | 4550 ms | 7.81 s |
| 13:38:41 | **冻结** | 17711 ms | 21.00 s |
| 13:46:26 | **冻结** | 8048 ms | 11.34 s |
| 13:58:19 | **冻结** | **46737 ms** | **50.03 s** |
| 15:13:41 | **冻结** | 1256 ms | 4.52 s |
| 15:40:03 | **冻结**（新判据首次） | 3271 ms | 6.57 s |

**时间分布值得注意**：凌晨 01:05~03:00 的 **115 分钟里一次都没有**，而 **13:39 / 13:46 / 13:59
三次集中在 22 分钟内**。当时接线与环境未变，诱因未定（见 §3.3）。

## 2. 现场日志特征（快速识别是不是它）

冻结发生时的"指纹"非常固定：

**USB Host 侧（M 板 `Host HID统计`）**：

- `reports` 与 `vendor_reports` **同时定格**，连续多个统计周期完全不变；
- `control` 计数也停止增长；
- `urb_to` / `control_fail` / `urb_retry` **开始增长**（正常运行时它们恒为 0，见 §3.2 末条）；
- 日志出现 `vendor_urb: 控制传输超时（800 ms）：挂为孤儿等待回收`。

**板间链路侧（同一时刻的 `UART1统计`）**：

- `tx/rx` **照常增长**、`peer=online`、`frame_err=0`、各队列 `drop=0`。

> **关键鉴别点**：`UART1` 一切正常而 `Host HID统计` 整体定格 ⇒ **问题只在 USB Host 一侧**，
> 不是链路、不是队列、不是丢包。

**恢复后**：自动出现 `HID接口发现` 与 `动态鼠标输入已启动`，`reports` 从 0 重新爬升。

## 3. 原因推测

### 3.1 与上游已复现问题相似（本机根因未定）

**ESP-IDF issue #14996 / IDFGH-14198「USB Host sometimes freezes randomly」**

| 项 | 内容 |
|---|---|
| 首次报告 | 2024-12 |
| 官方复现 | 2024-12-19 由 Espressif 确认复现 |
| 官方定性 | 2025-02-13 判为**疑似 ESP32-S3 USB Host 硬件勘误（HW erratum）** |
| 修复情况 | 两个 hotfix（其一为"HID RX 回调只做 memcpy、尽快返回"）在官方测试者处有效，**在报告者处无效** |
| 最新状态 | 2025-10-24 仍有新报告，**issue 至今 open** |

**本项目的相似症状**：19:56:03 与 20:48 起各一次，`reports` 与 `vendor_reports` 同时冻结
（跨一次板复位仍为 0），`urb_to` 累计到 10、`control_fail=5`，**EP0 控制传输全部超时**
（`urb_sub 379 − urb_ok 369 = 10 = urb_to`）；而桥接侧全程健康。点击鼠标无法唤醒，当时通过复位恢复。这些记录将断点收窄至 M 板 USB Host 路径，但未采集物理 USB 总线数据，不能确认与上游 issue 同一根因。

### 3.2 已排除的假设（附否证依据）

| 假设 | 否证依据 |
|---|---|
| 移动浅队列/合并导致 | 浅队列实测丢弃过多、手感明显变差；合并把报告率压到约 30 Hz |
| 主机 EXE 用 DTR/RTS 拽复位脚 | 代码级否证：EXE 打开串口时 `DtrEnable=false`、`RtsEnable=false` |
| 板载写盘饿死控制传输 | A/B 否证（写盘暂停轮次同样出现过冻结） |
| 移动占满 IO | 受控 A/B 否证 |
| "有源 Hub / 供电反灌"诱发 | **接线与环境未变时同样发生**（13:39/13:46/13:59 期间用户未动过接线） |
| 判据会因"设备偶发慢响应 + 用户没动鼠标"误触发 | 实测控制传输**最大延迟仅 1.7~3.7 ms**，与 800 ms 超时阈值差约 **216 倍**；且 `control_fail`/`urb_to`/`urb_retry` **在正常运行期间从不增长**（全量日志 8 次异常事件零误报） |

> 最后一条尤其重要：它把"控制请求失败"确立为**零误报**的冻结信号，是当前判据的基础。

### 3.3 仍存疑、尚未定论的诱因

- **13 点后频次明显升高**（22 分钟 3 次 vs 凌晨 115 分钟 0 次），当时接线与环境未变，原因不明；
- 是否与 **USB 总线负载、环境温度、供电质量**相关，未做受控实验；
- 上游已定性为疑似硬件勘误，因此**应用层的任何"根治"尝试都缺乏依据**。

## 4. 当前解决方案（应用层自愈链）

因为无法根治，方案是"**尽快发现 + 自动恢复**"。

### 4.1 判据（两级，先后收紧）

**第一代（2026-09-27）**：`数据冻结 ≥1 秒` **且** `该窗口内有控制传输失败`。

- 短板：**冻结期间若外部软件（如 G HUB）恰好不发控制请求，就没有"失败"可用**——
  13:58 那次因此白等了 **42 秒**。

**第二代（2026-09-28，当前）**：**USB 心跳探测连续 2 次失败**。

- 每 **0.5 秒**主动发一笔 `GET_DESCRIPTOR(Device)`（所有 USB 设备必答、正常不 STALL），
  超时 **200 ms**；
- 成败直接写入既有的 `s_last_ctrl_ok_us` / `s_last_ctrl_fail_us`，**完整复用原判据**；
- **不再要求"数据冻结"** ⇒ 刚上电、鼠标静止时同样能判，发现延迟由 ~1.3 s 降到 ~1.0 s（理论值）。

### 4.2 恢复动作

**二级恢复：根端口断电重枚举**——`usb_host_lib_set_root_port_power(false)` → 等 300 ms →
上电 → 等 1500 ms 让设备重新枚举，随后自动重传 Profile 并重建克隆。

**为什么不用一级（重挂接口）**：现场证实一级的 `hid_host_device_stop/start` 会被**在飞传输挡住**
而卡死任务，导致端口断电这条永远没机会执行（`port_cycle` 恒为 0，只能人工复位）。
修复后把二级**提到一级之前**执行。

### 4.3 实测效果

**分段耗时（5 次真实重置）**：

| 阶段 | 范围 | 稳定性 |
|---|---|---|
| ① 检测（冻结→判据） | 1256 ~ 46737 ms | ❌ **唯一变量** |
| ② 断电指令→上电完成 | 294 ~ 305 ms | ✅ 等于代码里的 300 ms 延时 |
| ③ Profile 传输 | 1039 ~ 1077 ms | ✅ 极稳 |
| ④ **总恢复**（判据→完成） | 3261 ~ 3295 ms | ✅ **极稳** |

**结论：总中断 = 检测段 + 恒定 3.29 秒**，恢复段已无压缩空间，优化全部集中在检测段。

> **⚠ 2026-09-28 更正（同日另一轮会话证伪，务必以此为准）**：上表"Profile 传输 1039~1077 ms"
> 曾被理解为 **Profile 全量重传的耗时**，**该理解不成立**。实测拆解如下：
>
> - **数据段本身极短**：P 侧 `OFFER 确认` → `收到完整物理HID Profile` 实测仅 **12 ms / 18 ms**；
> - **1070 ms 的真实来源**是 M 侧 `LINK_COMMIT_RETRY_INTERVAL_US = 1 s` 到点重放 COMMIT，
>   而 P 对"重复 COMMIT"会**立即回一条成功 ACK**（与真实挂载完成无关）；
>   P 挂载 <1 s 的样本里 M 侧实测 **642~667 ms**，恰好等于该重试间隔；
> - **真正的大头是 P 侧"卸载 → 安装 → Windows 重新枚举"**：实测 **609~962 ms（典型）**，
>   尾部可达 1662 / 2409 / 2712 ms。
>
> ⇒ **只跳数据重传的收益约 20~100 ms，不改变鼠标可用时刻**；因此实际采纳的是
> **"连卸载+重装一起跳过"**的方案（见 §7）。证据：`artifacts/tests/churn-P.log`、
> `artifacts/tests/soak-{P,M}-20260927-213209-soak-1h-run4.raw.log`（OFFER 2282005 → ACK 2283077）。

**各版本对比**：

| 版本 | 检测段 | 总中断 |
|---|---|---|
| 旧判据（等外部软件发请求） | 1256 ~ 46737 ms | 4.52 ~ 50.03 s |
| 新判据 + 500 ms 超时 | 3271 ms | 6.57 s |
| **新判据 + 200 ms 超时（当前）** | 预期 ~1.5 s | 预期 ~4.8 s |

**安全性验证**：200 ms 版本下 `hb_ok` 以 2 Hz 增长、**`hb_fail=0`、`port_cycle=0`**、
`ctrl_lat_max_us` 仅 3.2 ms ⇒ **零误报**，探测未拖慢正常控制传输。

## 5. 搜索到的外部信息汇总

- **Issue**：ESP-IDF **#14996**（对应 **IDFGH-14198**）「USB Host sometimes freezes randomly」；
- **官方时间线**：2024-12 报告 → 2024-12-19 复现确认 → 2025-02-13 疑似硬件勘误 →
  2025-10-24 仍有新报告，**至今 open**；
- **hotfix 情况**：两个 hotfix 均未在报告者处解决问题，其中包含官方验证过的缓解方向
  （"让 HID RX 回调尽快返回"）；本项目也已按该方向做过**回调瘦身**
  （1 kHz 路径不再调用 `hid_host_device_get_host_params()` 之类的组件查询）；
- **升级路径**：本项目**已使用最新组件**（`espressif/usb` 1.5.0、`espressif/usb_host_hid` 1.2.1），
  **无升级可解**；
- **社区共性**：报告者与官方测试者的结果不一致，说明与具体硬件/配置相关，**不是纯软件 bug**。

## 6. 可观测指标与判读

M 板 `Host HID统计` 行末尾的相关字段：

| 字段 | 含义 | 判读 |
|---|---|---|
| `reports` / `vendor_reports` | 鼠标/厂商报告累计数 | 连续多周期不增长 = 数据冻结 |
| `control` / `control_fail` | 控制传输次数/失败数 | **正常运行 `control_fail` 恒为 0** |
| `urb_to` / `urb_retry` | URB 超时/重试 | 只在冻结期增长 |
| `ctrl_lat_max_us` / `slow10` / `slow100` | 控制延迟峰值/超 10ms/超 100ms 次数 | 正常仅数 ms |
| **`hb_ok` / `hb_fail`** | 心跳探测成功/失败次数 | `hb_fail` 是**零误报**的冻结前兆 |
| `recover` / `port_cycle` | 一级/二级恢复触发次数 | 冻结事件计数 |

配套日志关键字：`心跳探测连续 N 次失败`（判据触发）、`二级恢复第 N 次：根端口断电重枚举`、
`根端口 power off=… on=…`、`恢复事务[profile_ack]`（恢复完成）。

## 7. 未验证与后续

- ⚠️ **200 ms 版本在真实冻结下的检测耗时尚未观测**（需等下次冻结发生）；
- ✅ **Profile 复用已实施**（2026-09-28 同日另一轮会话，`app 0x76b30`）：按用户决策采用**跳过"卸载+重装"整体**的方案，而非只跳数据重传（后者的真实收益仅 20~100 ms，见 §4.3 更正）；同轮新增 UART0 顶层诊断命令 `0x1C`（强制 M 重新采集 Profile 并重新提议）用于**按需复现**该故障段。**遗留**：`docs/审计.md` 中"提前成功 ACK 的准确性问题"仍是**未修的 Known Issue**；
- 上游 issue 若有新进展（官方定位到根因或发布修复），应重新评估是否需要自愈链。

## 8. 2026-09-29 无 reset 实施状态

上文第 4 节记录的是**已刷板的历史端口断电方案**。当前工作区按“避免 reset/端口断电造成物理鼠标不可用”的要求改了源码；较新的同源镜像已刷入 M/P 两板，正常 Profile 安装、移动和点击有现场证据，**随机冻结时的无 reset 恢复仍未验收**：

- M 侧 HID 输入回调只取原始报告、复制布局快照并非阻塞入队；诊断、位移解析、样本日志移到工作任务。`usb_host_hid` 1.2.1 用项目内可跟踪的本地组件覆盖，补 IN 接收重提交结果检查和限次重试。
- EP0 的 SET_REPORT、GET_REPORT 均用独立 URB；超时回调与等待线程用原子状态决定唯一释放者，最多保留 4 个未完成孤儿。到达上限时新控制请求失败，保持现有输入通道。
- 心跳连续失败只表明 EP0 异常；物理鼠标报告仍在到达时继续转发。输入也停滞时只释放按钮。自动接口重挂和根端口断电由 `USB_HOST_AUTOMATIC_DESTRUCTIVE_RECOVERY=0` 关闭，克隆会话保持。
- ESP-IDF 6.0.2 自定义分区下构建 `Pass`，纯逻辑回归 `Pass`；2026-09-29 同源镜像 SHA-256 为 `83191D2DFF74615E2CC3BE8B2ADCAE91DCF9857E6B27DB6C0B032E1B0D648561`。**完整 USB Host 冻结后能否不 reset 恢复仍未验证，当前也没有可保证成功的软恢复。**若实测整机停止传输，必须明确判失败，再依据总线和端点证据设计下一步。
