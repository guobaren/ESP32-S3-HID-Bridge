2026-10-13 用户重插后，M CherryUSB Host 成功枚举并发布完整 Profile。通过 M UART0 的只读 `DIAG_PROFILE_READ` 分块读取现有 cache；DEVICE_HELLO nonce 确认 COM13 为 M。Profile 长度 465 B，CRC32 `967CCF69`，flags=0（非 partial）：

| Interface | Subclass / protocol | Report descriptor 长度 | 描述符字段对应类型 |

接口 2 的 98 B HID report descriptor：

- CRC32：`102142E5`

| Report ID | Input 正文 / 含 Report ID | Output 正文 / 含 Report ID |

同一只读快照窗口中 COM13=M、COM3=P；M diagnostics 为 `connected=true`、`stopping=false`、`profileReady=true`、`enumerate_success`，P 为 `mounted=true`、`lastResult=mounted_acked`。此证据支持本次成功枚举与克隆挂载，但没有在该次读取中单独控制并记录用户的移动/点击/滚轮动作。M/P R3→R4 uptime 分别增长 69,464/69,448 ms，与墙钟 69,456/69,442 ms 接近，没有复位迹象。

用户之后再次重插，同一固件成功枚举；当前完整 465 B cache 包含接口 2 的 98 B 描述符。因此能确认此前 NAK 是那次枚举的直接失败结果，且同一接收器后来可成功获取并克隆该接口；NAK 的底层原因仍未知。历史失败当时 CherryUSB HID class 将描述符请求的负返回交给枚举层，hub 随即终止该次枚举（`firmware/managed_components/cherry-embedded__cherryusb/class/hid/usbh_hid.c:263-266`、`firmware/cherryusb_overrides/usbh_hub.c:680-688`）；该历史路径未做有限请求级重试。不得跳过接口 2。

### 2026-10-14 有界描述符请求重试（源码/构建验证，未部署）

### 读取与证据边界

- 当前 98 B 是从成功枚举生成的 M Profile cache 读取的，不是一次新发起且由 UART0 返回完整 payload 的 EP0 `GET_REPORT_DESCRIPTOR`。
