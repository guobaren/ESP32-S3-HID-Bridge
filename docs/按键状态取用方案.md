# 副机按键状态取用方案（A5 推送 + 共享内存）

本文记录设计决策、源码实现和验证边界。2026-10-10 的协议、固件、Host 与 Sender 对接已完成构建/专项夹具；同一主镜像已刷至两板，M UART0 的模式切换、ButtonState 帧暂停/恢复及 Host SerialBridge→MMF 实机组件集成已通过。实机状态帧全部 `valid=0`，所以真实按键映射、按钮释放、光标消费、精确心跳周期和长时运行仍待验收。第 3 节保留实施前源码快照供追溯，不能作为当前源码状态。

## 2026-10-10 已确认的设计基线（优先于下文历史草稿）

- **状态协议**：A5 上行 `0x1F` 的 1 字节指 payload，不是整帧；完整帧为 10 字节。payload 的 bit0..4 是原始物理按钮（bit0 左、bit1 右、bit2 中、bit3 侧键1、bit4 侧键2），bit7 是有效位，bit5..6 保留为 0。不上报屏蔽后的第二种状态，不加屏蔽掩码，不设 `rawButtons` 字段。Makcu `button_mask` 是物理按钮转发抑制配置，不是 0x1F 五个状态位的掩码，也不应用于本状态上报。
- **运行模式**：EXE/A5 默认 921600；固件 Makcu 运行时上电默认关闭，编译支持可保留。用户在 EXE 中手动开启 Makcu 后切到 115200，EXE 继续持有 M UART0，直到用户真正退出 EXE。Makcu 使用结束后，关闭其它串口占用，再重开 EXE并手动关闭 Makcu，恢复 A5/921600；不在线交接、不按波特率或任意 V4 字节自动切换。115200 Makcu 模式必须暂停按键状态 A5 推送，以免 V4 流被混入 A5 帧。
- **软件鼠标平滑**：普通非物理软件 MouseReport（A5/UDP 与 Makcu 生成的标准报告）由 M 端共用现有 `m_udp_smoothing` 平滑一次，传给 P 的槽字段为 0，P 不重复平滑。物理鼠标 raw 转发及 `DIAG_REPORT_INJECT_REQUEST` 专用原始报告注入保持保真直通，不擅自改写。Python sender 不在本轮实施范围；直连 Makcu sender 也不在本轮范围。
- **共享内存**：总长 64 字节，偏移 32 `buttons` 存原始物理 bit0..4；偏移 33 是 `reserved=0`，不设 `rawButtons`。Host 与 sender 必须用同一命名 mutex 持锁访问全部头部/状态/seq；`seq` 只是版本号，不能替代锁。锁忙不刷新缓存时间，仅在先前完整有效快照未超过 200 ms 时沿用；弃锁后本轮快照作废并等 Host 完整重发布，不能把下一次拿到锁或残留字段当作有效。时间戳用 `Stopwatch.GetTimestamp()/Stopwatch.Frequency` 的 QPC 统一时基。Host 映射名默认 `HidBridge.Buttons.v1`，保存在 `AutomationSettings.ButtonStateMappingName`；对应 mutex 名为映射名加 `.Mutex`。缺少该字段或配置为空白时回退默认值。
- **名称设置**：EXE 设置页提供单独的“保存名称”按钮；输入会 Trim，空白、NUL、命名空间前缀之外的反斜杠会友好拒绝。Windows `Local\` / `Global\` 前缀仅在名称开头且大小写正确时允许。名称必须与 Sender `config.ini [aim] third_party_buttons_map` 完全一致。保存不热替换当前 publisher，重启 EXE 后生效；未提交的文本不会被其他开关操作保存。
- **发送与预算**：状态变化在下一控制循环尽快推送；另每 5 ms 目标间隔重复发送含 `valid` 的完整当前状态，持续按住也刷新共享内存 timestamp/seq。失败保留 dirty 并在下一控制循环立即重试最新完整快照，每循环最多尝试一次、无忙循环；只有成功才更新 lastSent/time，generation 比较避免发送期间的变化被清掉。仅能检测本地写失败，无端到端 ACK，心跳用于恢复丢帧。5 ms 对应 200 帧/s、2000 B/s；8N1 理论占用约 2.17%@921600，17.36%@115200。主预算是 921600；1–2 ms 是未验证预算，5 ms 是任务目标，不是精确实时保证。原单 int 微基准不代表有锁完整读取实测。
- **当前实施状态**：`0x1F` 双向订阅/状态、M 上电 Makcu runtime 默认关闭与 `0x37/0x38` 显式模式切换、Host 的 64 字节共享内存发布、Sender 共享内存读取，以及普通软件鼠标报告在 M 侧共用平滑队列均已落入源码。Host 另已支持在设置中持久化自定义共享内存名并于启动时创建对应 MMF/mutex；本轮设置页/旧配置兼容/非默认命名对象 focused checks 已通过。固件 V4 ON/OFF 构建、固件 native checks、Host Release/格式检查及专项检查通过；Sender 与 Host 的独立跨进程夹具由主代理复核为 29/29。相同主镜像 SHA256 `1107F7BBEED3F9ABBE45CBF47C2F24AD0A62DE6927D06B1AC5AEC94B3343ADCB` 已刷至 COM3=P 与 COM13=M；刷后两板 921600，M/Makcu OFF。真实串口 ON/115200 与 OFF/921600 查询和角色复核均通过；ButtonState 2.391 s 收到 409 帧、ON 1.031 s 为 0 帧、恢复后 2.391 s 再收到 409 帧，但 `valid=0`。此前 Host 最终 DLL 在默认名称下真实 COM13 完成模式开关和 MMF 发布实测，MMF `validBits=2→0→2`、seq `5→8→18`；**当前新增的自定义名称设置尚未做实机/Sender 业务链路验证**。构建、检查和实机结果见 `artifacts/tests/button-state-20261010/` 与 `artifacts/tests/button-state-mapping-name-20261010/`。以上不证明实体按键或光标行为；没有新增独立“发送失败计数器”，实现的是本地 TX 失败检测与下一控制循环重试。Python sender 不在本轮范围。

## 1. 需求与问题

部署形态（用户确认）：

```
物理鼠标 ──USB──> M 板 ──UART1──> P 板 ──USB──> 主机（运行游戏 / 接收 aim 输出）
                    │
                    └──UART0──> 副机（Host EXE 与 sender 都运行在这里）
```

- C# sender 与 Host EXE 都在**副机**；sender 在副机采集截图并发送给主机。sender 界面的 `get_img_model` 会同步给 `run.py`，不能因为 sender 在本机截图就把它设为 `local`：`run.py` 处于 `remote` 时读取收到的 `keyBits`，处于 `local` 时读取主机本机 `GetAsyncKeyState`。本方案只影响 `remote` 的按键判定链路。
- 物理鼠标接在 **M 板**上，M 板只把 UART 接到副机；**副机看不到鼠标这个 HID 设备**（不是"被抑制"，而是物理上不在副机的 USB 总线上）。
- 因此 sender 无法用 `GetAsyncKeyState`，也无法用 Raw Input 拿到"用户真实按下的那个键"——副机上两者都只能看到副机自己的键鼠。

要解决的问题：**在副机上取得 M 板上那只物理鼠标的按键状态**，供 sender 判定瞄准按键。

## 2. 目标与非目标

**目标**

1. C# sender 能把 M 板物理鼠标 5 个按键（左、右、中、侧键 1、侧键 2）的当前状态送入 `keyBits`，供 `run.py` 的 `remote` 按键判定使用。
2. 端到端延迟与现有链路同量级（约 1–2 ms），不因新增功能拖慢输入转发或克隆。
3. Host EXE 与 C# sender 可同时运行；sender 从共享内存取状态，不直接占用 M UART0。
4. 默认 EXE/A5 使用 921600。Makcu 模式由用户在 EXE 中手动切换为 115200；EXE 保持串口占用直至进程真正退出。结束 Makcu 使用后关闭其它串口占用，重开 EXE 并手动关闭 Makcu，恢复 A5/921600；不做在线交接。
5. 普通非物理软件 MouseReport（A5/UDP 与 Makcu 生成的标准报告）统一在 M 侧平滑一次，P 不重复平滑；物理 raw 转发和专用原始诊断注入保持保真直通。

**非目标**

- 不提供主机（P 侧）键盘状态的获取——P 是 USB Device，物理上无法读取主机的键盘输入（见 §3.3）。
- 不改变 sender→主机的线协议：按键通过既有 `keyBits` 位图传递（§6.3）。
- 不实现 sender 直连 M 的 Makcu 按键查询；该路线与 Host EXE 争用同一块 M 板 UART0，详见 §3.2、§6.3。

## 3. 实施前源码快照与硬约束（2026-10-10；保留作历史依据）

> 本节关于旧实现的描述是本方案实施前的源码快照。当前实现状态以本文开头、§5.7、§9、§10、§12 和 [docs/protocol.md](protocol.md) 为准。

### 3.1 M 板 RAM 里已有物理按键状态

`s_makcu_v4_physical_buttons` 由 M 侧鼠标报告处理路径更新：

- 写入点：`firmware/main/hid_host_mouse.c:974-985`，从真实 USB 鼠标报告解析按钮后调用 `dual_uart0_control_v4_physical_buttons(physical_buttons)`；注入报告不会进入这条物理状态路径。
- 缓存与 Makcu 边沿队列：`firmware/main/uart0_control.c:228-253`，缓存限制为 5 位 `0x1F`。
- 当前解析器从描述符报告中第一个按钮字段起按顺序取最多 5 位（`firmware/main/hid_report_layout.c:433-454`）。这些位到左/右/中/侧键1/侧键2的语义映射依赖鼠标报告描述符，需在目标设备验证；本方案的目标映射在 §6.3 明确列出。

按钮状态共用一条解析和缓存路径；目标设备是否按预期顺序提供五个按钮位，仍须逐键验证。

### 3.2 M 的 UART0 协议路由与输入所有者

M 板处于鼠标 Host 角色时，控制任务通过 `uart0_protocol_router_feed()` 路由 UART0 字节。路由器在相应解析器状态下识别 A5 帧或 Makcu V4 命令（`firmware/main/uart0_control.c:2127-2149`、`firmware/main/uart0_protocol_router.c:22-49`）；完整且通过检查的 A5 帧可选择 A5 输入所有者，成功的 V4 命令也可选择 V4 输入所有者（`uart0_control.c:2011-2043`）。所以这是可切换的协议解析和输入所有者，不应描述为一方启用后另一方解析器必然永久停用。

实现约束：

- Host EXE 的 A5 订阅客户端与 sender 直连 M 的 Makcu 客户端不能同时作为同一 M UART0 的活动控制客户端；两者会争用串口并可能切换输入所有者。互斥只针对这两个使用同一 M UART0 的客户端，不意味着 sender 本机输入与 EXE 共享内存输入互斥。
- 新增订阅和状态推送使用 A5 `0x1F`。当前 `routed_a5()` 只放行到 `0x1D`，所以订阅命令会在路由处被丢弃；实现时需显式加入 `0x1F`，未知类型仍不得抢占输入所有者（§5.0）。
- A5 状态报告的语义独立于 Makcu V4 的按键查询和屏蔽行为。Makcu 的 `button_mask` 是转发抑制配置，且 `dual_uart0_control_v4_get_physical_masks()` 仅在 V4 owner 下返回该配置（`uart0_control.c:278-294`）；它不是本方案状态字节的五个按键位，也不能直接作为 A5 状态过滤掩码。

### 3.3 主机键盘无法经 P 获取

- P 锁定为 `PC_DEVICE` 角色，只安装 TinyUSB device（`firmware/main/pc_hid_output.c:2352`，`tinyusb_driver_install`）。
- USB Host 库只在 M 侧安装（`firmware/main/hid_host_mouse.c:2114-2125`，`usb_host_install`）。
- 因此 P 对主机而言是"一只鼠标"，主机的键盘不在它的 USB 总线上；读主机的 raw input 需要以 USB Host 身份接收键盘 HID 报告，现有接线与固件下都做不到。

要拿主机键盘只有三条路：主机上加代理程序读 raw input 再转给副机；加一块独立的 USB Host 嗅探板与键盘串联；专用 USB 抓包硬件。**本方案不涉及。**

### 3.4 副机侧两条本地通路都不可用

| 通路 | 为何不可用 |
|---|---|
| `GetAsyncKeyState` | 只能看到副机自己的键鼠状态；物理鼠标不在副机 |
| Raw Input | 同上；且副机没有该鼠标的 HID 设备节点 |

（顺带记录一个已验证的性质，供未来参考：若 EXE 处于捕获模式并用低级钩子抑制本机输入，Raw Input 仍能穿过抑制读到**本机**物理输入——本机实测抑制窗口内 4514 条 Raw Input 鼠标事件、左键按下正常，同窗口 `GetAsyncKeyState` 全程为 False。该性质在本方案中用不到，因为鼠标不在副机。）

### 3.5 sender 现有的按键用法（决定了输出形态）

- 本轮只覆盖 C# sender：`D:\YOLO_Project\sender-csharp\WindowsInput.cs` 读取发送端本机按键并生成 256 位键码位图；Python sender 不在本方案实施范围内。
- 线协议：`host` 无关，见 `D:\YOLO_Project\sender-csharp\WireProtocol.cs:148-190`，其中 `KeyBits` 为 32 字节（256 位虚拟键位图）。
- 主机侧判定：`D:\YOLO_Project\run.py:509-531`。`get_img_model == "remote"` 时用收到的 `key_bits` 判定；`local` 时用主机本机 `GetAsyncKeyState`。C# sender 本机截图并不意味着 `run.py` 是 `local`。

**关键推论：按键只要映射成虚拟键码位写进 `keyBits` 即可，sender→主机的线协议零改动。**

## 4. 方案总览

```
物理鼠标按键
   │  (M 的鼠标报告处理任务，每个有效报告)
   ▼
M 固件：更新状态 generation/dirty；变化后尽快发送，另每 5 ms 发送完整心跳
   │  (UART0 控制任务，名义 1 ms 一拍；失败后下一循环重试)
   ▼
M 固件：A5 推送帧 0x1F（1 字节状态）
   │  UART0
   ▼
副机 Host EXE：SerialBridge 收到 0x1F 推送 → 更新共享内存快照
   │  命名共享内存（.NET MemoryMappedFile）
   ▼
副机 sender：按自身输入节奏读取 → 映射成虚拟键码位 → 写进 keyBits
   │  既有 TCP/USB 线协议（不变）
   ▼
主机 run.py：is_key_pressed_remote(key_bits, aim_button_key)
```

采用**推送式**而非轮询式：状态变化后由控制任务尽快发送；此外每 5 ms 目标间隔重发包含当前状态和有效位的完整快照作为心跳。这样即使状态持续按住，Host 仍能刷新共享内存时间戳；发生本地写失败或线路丢帧后，也能由后续重发恢复状态。5 ms 是任务调度目标，不是精确实时保证。

## 5. 固件层设计

### 5.0 必须先改的两处类型闸门（否则新命令到不了处理函数）

核实代码后确认，新消息号会被两处既有闸门拦掉，**这是必须先解决的前置改动**：

1. **A5 路由白名单**：`firmware/main/uart0_control.c:2034` 为
   `if (frame->type < DUAL_MESSAGE_KEYBOARD_REPORT || frame->type > 0x1DU) return;`
   —— 类型大于 `0x1D` 的帧在进入 `on_control_frame()` 之前就被丢弃（注释写明"未知消息不能抢走输入所有权"）。
   ⇒ 订阅命令与推送帧都用 `0x1F`，**必须落在被放行的类型集合内**，否则固件收不到订阅、EXE 也收不到推送。
2. **主机侧统计收集器**：`host/HidBridge.Host/Transport/SerialBridge.cs:226` 的 `OnDiagnosticFrame()` 目前只服务统计快照收集器（`_statsRequests.TryGet`），其余类型直接 `return`。
   ⇒ 推送帧必须在函数内新增分支处理（可放 `TryGet` 之前），且不得影响统计路径。

**由此推导出的协议号选择**（原 §5.1 的方案据此调整）：

| Type | 名称 | 方向 | Payload | 说明 |
|---|---|---|---|---|
| `0x1F` | `BUTTON_STATE` | 双向 | 下行（EXE→M）1 字节：`0` 退订 / `1` 订阅；上行（M→EXE）1 字节状态（§5.2） |

**为什么推送与控制共用 `0x1F` 而不是另选号**：`0x01..0x1D` 已被 A5 与 UART1 的既有定义占满且语义都已被占用（统计、诊断、Profile、厂商会话、UART1 链路消息），在其间插号既有语义冲突风险、又要逐个核对两张占用表；而 `0x1E` 之后的号段（`0x37` 等）有被 UART1 链路消息使用的可能。A5 帧的 type 字节在**两个方向上本来就是独立解读**的（`0x1D` 请求 / `0x1E` 响应、`0x28`/`0x2A` 等已是成对或分向定义的先例），因此"同号双向"最省号也最不容易撞号。

**实现约定（重要）**：实现时只新增**一个**成员 `ButtonState = 0x1F`，下行与上行都复用它，方向由调用点（发送订阅 / 解析推送）决定；固件侧同样只用一个 `DUAL_MESSAGE_BUTTON_STATE = 0x1F`。这样避免用两个枚举别名表达同一消息号。`docs/protocol.md` 登记时需明确写出"同一 type、载荷按方向解读"。

**实际放行策略**：固件按显式已定义号集合处理 A5 输入，允许 `0x1F` 订阅/退订，不会把 `0x1E` 或未知类型自动赋予输入所有权切换能力：

```c
/* 实际策略：只允许已定义类型；BUTTON_STATE (0x1F) 依方向处理。
   未知类型仍然丢弃，不抢输入所有权。 */
if (!dual_message_type_known(frame->type)) return;
```

实现位置：`firmware/main/uart0_control.c` 与 `firmware/main/uart0_protocol_router.c`；对应路由与处理策略已纳入固件 native 检查。

而不是简单地把上限从 `0x1D` 上调到 `0x1F`——后者会让 `0x1E`（统计响应）与将来任何新号都自动获得"抢所有权"的资格，违背该行注释的原意。

### 5.1 消息号定稿

| Type | 名称 | 方向 | Payload |
|---|---|---|---|
| `0x1F` | `BUTTON_STATE`（固件：`DUAL_MESSAGE_BUTTON_STATE`；C#：`MessageType.ButtonState`） | 双向 | 下行 `{0}` 退订 / `{1}` 订阅；上行 1 字节状态（编码见 §5.2） |

`0x1F` 的选择依据：`0x1E` 已被 `STATS_SNAPSHOT_RESPONSE` 占用（`firmware/main/bridge_protocol.h:17-92` 与 `shared/HidBridge.Protocol/MessageType.cs`），`0x1F` 在 A5 命名空间内空闲。Makcu V4 opcode（如 `0x10`/`0x55`）属于另一个协议栈；M 的 UART0 路由器根据解析状态分派两种格式，输入所有者可切换，详见 §3.2。

A5 帧结构（以代码为准，`shared/HidBridge.Protocol/FrameCodec.cs`）：

```
[A5 5A] [version=2] [type] [sequence:u16le] [payload_length:u8] [payload:0..64] [crc16:u16le]
  2         1         1        2                 1                  N            2
总长 = 9 + payload_length，CRC16 覆盖 [version..payload]（CCITT，初值 0xFFFF）
```

- 载荷上限 **64 字节**（`FrameCodec.MaximumPayloadLength`）；本方案用 1 字节。
- `FrameCodec.TryDecode()` **不校验 type**（任意类型字节都会被解出 `BridgeFrame`），type 过滤只发生在固件的 `routed_a5`；因此 EXE 侧能收到推送帧的前提只是"固件肯发"。
- 本方案上行状态 payload 为 **1 字节**；这不是整帧长度。含 7 字节 A5 头、1 字节 payload 和 2 字节 CRC 的完整状态帧为 **10 字节**。
- 推送帧的序号语义：固件侧每发送一帧递增序号，接收端不依赖序号判断共享内存撕裂；序号行为仍需与协议编码器保持一致。

### 5.2 状态字节与屏蔽语义（已定）

上行 A5 **payload** 只有 1 字节，完整 A5 状态帧仍为 10 字节（§5.1）。编码如下：

```
bit0..4  原始物理按钮：bit0 左键、bit1 右键、bit2 中键、bit3 侧键1、bit4 侧键2
bit5..6  保留，发送为 0
bit7     有效性：1 = 当前 M 鼠标接口状态有效；0 = 当前状态未知/无鼠标/输入失效
```

掩码语义：

- payload 固定上报原始物理按钮，不应用 `button_mask`。`button_mask` 是转发抑制配置，不是状态 payload 的五键掩码或过滤开关。
- 一个字节只能表达一份五键状态与一个有效位；本方案不加屏蔽掩码，不声称能从单字节还原原始与有效两种独立状态。
- `bit7` 必须随当前鼠标有效性变化：订阅后无鼠标时仍发送 `bit7=0` 心跳；最后一个鼠标接口断开、停止或当前状态被清理时，尽快发送有效位清零的状态。不能把“历史上收过报告”当作永久有效。

### 5.3 数据流与热路径（关键设计）

```
M 鼠标报告处理任务（报告率最高约 1 kHz）
    └─ 更新原始状态快照；若状态/有效性变化，增加 generation 并置 dirty
       只做短临界区内的快照更新，不发送串口

UART0 控制任务（CONTROL_POLL_MS = 1，名义 1 ms 一拍）
    ├─ dirty：下一控制循环尽快发送最新完整状态
    └─ 距上次成功发送达到 5 ms：发送完整状态心跳（含 valid）
       每个循环至多尝试一次，TX 采用有界、非阻塞写入
```

**禁止在 USB Host 输入回调或报告处理路径里直接写串口。** `dual_uart0_output_write*` 路径含互斥与 `wait_tx_idle`（`firmware/main/uart0_output.c:144-175`），从输入热路径取该锁会阻塞输入。当前物理按钮解析路径更新快照，Makcu 订阅再将边沿入队并由 UART0 控制任务发送（`firmware/main/uart0_control.c:228-250` 与 `583-624`）；本方案沿用任务发送结构。

发送与并发约定：控制任务在短临界区内复制状态和 `generation`，离开临界区后组帧并尝试有界非阻塞写入。写入失败时不清 `dirty`、不更新成功发送时间；下一个控制循环重试最新完整状态，每循环最多一次，不忙循环，也不等待新的 USB 输入。写入成功后只在当前 `generation` 仍与发送快照一致时清 `dirty`、记录 `lastSent`；若发送期间状态变化，则保留 `dirty`，让下一循环发送新状态。这样不会因较早的发送完成而吞掉并发的新变化。

TX 成功仅表示本地写入/有界队列接受成功；当前协议没有 Host 对每帧的端到端 ACK，无法确认对端实际收帧。5 ms 状态心跳用于恢复本地队列接受后丢失的状态帧。

### 5.4 为什么不用事件队列

Makcu 订阅用 64 槽环形队列（`MAKCU_V4_EVENT_CAPACITY = 64`），因为它要给出**每次按下/松开的边沿**。本方案的消费者是"按键状态"，而状态是幂等的：

- 中间态被合并、甚至"按下+松开"落在同一拍内被合并，都不影响消费者读到的最终状态正确性；
- 因此按键数据可使用最新完整快照、generation 和 dirty 状态；USB 回调不排队每个边沿。5 ms 心跳和失败重试也发送当前完整快照，不承诺点击边沿序列。

若将来需要边沿顺序（例如统计点击数），再改为队列。

### 5.5 开销核算

| 项 | 设计预算/估算 |
|---|---|
| RAM | 不再按 3 字节估算；需计入当前/上次状态、generation、dirty、订阅状态、心跳时间和有界 TX 缓冲，具体值以实现为准 |
| 输入回调 CPU | 更新短快照、必要时增加 generation 并置 dirty；尚未测量，不标注纳秒级结论 |
| 控制任务 CPU | dirty 时或心跳到期时最多一次有界非阻塞写尝试；组装完整 **10 字节**帧 |
| 线路 | 5 ms 心跳目标为 200 帧/s × 10 字节 = **2000 字节/s**，另加状态变化帧。按 8N1 每字节 10 bit 估算，占用约 **2.17%@921600**、**17.36%@115200** |

以上为协议和任务配置推导的理论预算，未在目标板实测。M UART0 的实际波特率、控制循环调度、USB 输入周期和 TX 队列行为都会影响结果；1 ms 是任务周期目标，不是精确实时保证。

### 5.6 失效与边界

- 未订阅：保留最新状态；收到订阅后标记 dirty，下一控制循环发送完整基线。无鼠标时也发送 `valid=0`。
- TX 缓冲满或本地写失败：保留 dirty，并在下一控制循环重试最新完整状态；不等下次按键变化。每循环至多一次，使用有界非阻塞写入。当前没有端到端 ACK，心跳承担丢帧后的状态恢复；实现没有新增独立本地失败计数器。
- 状态在发送期间变化：依据 generation 比较，只在发送快照仍为最新时清 dirty；否则下一控制循环继续发送。
- 5 ms 心跳：每次成功发送完整状态（包括 `valid`），更新时间；失败不更新成功发送时间，下一循环重试。
- M 未枚举鼠标、最后一个鼠标接口断开或输入状态失效：当前按钮状态清零或标未知，并把 `valid` 置 0；这个变化需尽快经 A5 推送，随后继续发送 `valid=0` 心跳。
- 退订：`0x1F` 下行 payload `{0}`；Host 在正常退出、端口断开和模式切换时退订并清理状态。固件当前没有 A5 订阅超时租约，因此 EXE 异常退出时可能留下设备端订阅，直至 M 复位；状态心跳不是续租机制。

### 5.7 软件平滑统一（源码已实现，真机待验）

- A5/UDP 与 Makcu V4 生成的标准软件 MouseReport 都进入 M 侧同一个 `m_udp_smoothing` 队列；Makcu 模式下队列 tick 继续运行。源码位置见 `firmware/main/uart0_control.c`、`firmware/main/m_udp_smoothing.c` 与 `firmware/main/uart0_output.c`。
- M 发给 P 的软件报告槽数字段固定为 0，P 不重复平滑。普通软件输入在 M 侧只平滑一次。
- 输入所有者切换、取消、Release 与断连路径清理共用队列并释放软件按钮；`DIAG_REPORT_INJECT_REQUEST` 专用原始报告注入和物理鼠标 raw 转发保持原始路径。
- 源码与构建已检查；位移/滚轮/横滚守恒、真机按键释放及时序、物理 raw 保真及长时运行仍待实机验收。

### 6.2 共享内存布局（64 字节，全部小端）

| 偏移 | 类型 | 字段 | 说明 |
|---:|---|---|---|
| 0 | u32 | `magic` | `'H','B','K','1'` = `0x314B4248` |
| 4 | u32 | `version` | `1` |
| 8 | u32 | `mappingSize` | `64` |
| 12 | u32 | `reserved` | 0 |
| 16 | u64 | `seq` | 每次完整发布 +1，在同一互斥量内最后写入，作为版本号/新发布标识 |
| 24 | f64 | `timestampSeconds` | QPC 秒：`Stopwatch.GetTimestamp() / Stopwatch.Frequency`；两个进程在同一主机读取同一计时基准 |
| 32 | u8 | `buttons` | 原始物理按钮位，bit0..4 映射见 §5.2；不应用 `button_mask` |
| 33 | u8 | `reserved` | 置 0 |
| 34 | u8 | `valid` | bit0 = M 当前鼠标状态有效；bit1 = EXE 已订阅且处于 A5 状态推送模式 |
| 35 | u8 | `connectionState` | 0=未连接 1=已连接未订阅 2=已订阅（便于排障） |
| 36..63 | 28 字节 | `reserved` | 置 0；与 64 字节映射总长一致 |

约定：

- 映射名默认 `HidBridge.Buttons.v1`；互斥量名 `HidBridge.Buttons.v1.Mutex`（不复用截图链路会话私有的 GUID 命名）。Host 与 sender 必须使用同一个命名互斥量，并且**必须持锁读取/写入完整头部、状态字段和 `seq`**；不能把 mutex 当可选项。
- Host 只在锁内写共享内存字段并递增 `seq`，锁外执行串口读写。`seq` 标识一次完整发布；一致性由双方共同持有的 mutex 保证，不能仅凭“读两次 seq 相同”判断快照没有撕裂。
- sender 用 `WaitOne(0)` 非阻塞尝试获取锁。拿到锁后，在锁内读取并校验全部 64 字节布局、头部、状态和 `seq`，然后释放锁。锁忙时不刷新缓存时间；仅当上一份完整且有效的缓存仍小于 200 ms 时可继续沿用，否则本轮按未知处理并清零第三方按钮位。
- 若 `WaitOne` 抛出 `AbandonedMutexException`，.NET 已将 mutex 所有权交给当前进程，但共享内存可能停在写入中间态。记录此时的 `seq` 作为恢复门槛（不将它视为可信快照），释放 mutex，作废缓存并按未知处理；等待 Host 在锁内完整发布且 `seq` 超过恢复门槛、头部/状态检查通过后再恢复。Host 重启时应在同一 mutex 内承接并递增映射残留序号，完整重写头部和快照；不能把“再次取得 mutex”或残留旧字段当成有效快照。
- 不需要事件对象：sender 按自己的输入节奏读取。Host 每次收到状态帧都更新完整快照、时间戳和 `seq`；5 ms 心跳确保无按键变化时仍能刷新新鲜度。
- QPC 时间使用 `Stopwatch.GetTimestamp() / Stopwatch.Frequency` 换算为秒，不使用每个进程各自起点的 `Stopwatch.Elapsed`。EXE 退出时尽力写 `valid=0`；sender 超过 200 ms 没有收到新的有效完整快照时按未知处理（§8）。

## 7. 时序预算

| 段 | 耗时 | 出处 |
|---|---|---|
| 物理按键 → M 收到并解析 USB 报告 | 目标 ≤1 个报告周期；1000 Hz 时名义约 1 ms | 设备报告周期预算，非目标鼠标实测保证 |
| 状态变化 → 控制任务尝试发送 | 下一控制循环尽快发送；1 ms 为名义任务周期 | `CONTROL_POLL_MS = 1` 与调度配置；不是精确实时上界 |
| 10 字节 A5 状态帧线路时间 | @921600 约 0.11 ms；@115200 约 0.87 ms | 8N1、10 bit/byte 的理论计算 |
| Host 收帧、取得 mutex、发布共享内存 | 未测量完整路径 | 需实现后测量 |
| sender 非阻塞锁定并读取 64 字节快照 | 未测量完整路径 | 单字段旧微基准不代表本路径 |
| **到 sender 可见** | **约 1–2 ms 设计预算，不是保证** | 受报告周期、实际波特率、任务调度、Host 接收、锁竞争及 sender 采样节奏影响 |

参考实测（本次会话，同一台副机）：

- 历史参考：共享内存读一个 int 的微基准 **<0.05 µs**（10 万次批量平均；单次低于计时器分辨率）。它没有覆盖本方案的 64 字节布局、命名 mutex、完整校验和锁竞争，不能作为本方案读取时延实测。
- 历史对比：回环 UDP 请求/应答往返中位 **13.5 µs**（300 样本）、命名管道往返中位 **21–22 µs**；这些不是本方案的端到端比较结果。
- 历史对比：Makcu `0x55` 查询往返（直连 M）中位 **3.33 ms**（200 样本）；该路径与 Host EXE 共用 UART0，且本轮不实现直连 Makcu 输入。

以上历史数据只作背景。新方案的 1–2 ms 是待验证预算；5 ms 是心跳调度目标而非精确实时保证。需测量真实的 M UART0 波特率、完整 A5 到共享内存的耗时及 sender 读到状态的分布后才能给出实测结论。

|---|---|---|
| EXE 未运行 / 映射不存在 | `OpenExisting` 失败 | 视为未知：第三方鼠标 VK 位全 0，日志提示一次 |
| 头部不符 | magic/version/mappingSize 不匹配 | 拒绝使用，视为未知并记日志 |
| 未订阅或 M 无鼠标 | `valid` 相应位为 0 | 视为未知：第三方鼠标 VK 位全 0；M 无鼠标时仍会收到 `valid=0` 心跳 |
| 数据陈旧 | 上一份完整快照距当前 QPC 超过 200 ms | 视为未知：第三方鼠标 VK 位全 0 |
| mutex 正被 Host 持有 | `WaitOne(0)` 返回未获得 | 不等待；不刷新缓存时间。只在上一份完整有效缓存未超过 200 ms 时沿用，否则视为未知 |
| mutex 被遗弃 | `WaitOne` 抛出 `AbandonedMutexException` | 释放已授予的 mutex；本轮快照作废并视为未知，重新建立读取连接，等待 Host 完整发布新快照后恢复 |
| 快照并发读写 | Host 和 sender 使用同一 mutex | 双方都在锁内访问完整布局；不使用无锁双读 `seq` 作为一致性保证 |

**未知一律按"未按下"处理，绝不按"按下"处理**，避免误触发瞄准。

## 9. 当前兼容性、回收与风险

- **协议兼容**：`0x1F` 是一个双向类型，下行订阅/退订、上行完整状态；旧版 Host/固件不支持，部署时两侧需使用兼容版本。当前固件按显式类型策略处理 A5 帧，Host scanner 可从串口混合流拆出 ButtonState、MakcuModeStatus 与 DeviceHello，并保留既有统计帧处理；对应专项检查通过，真实 COM13 模式切换和 ButtonState 帧暂停/恢复已验证。物理状态有效值尚未观测到。
- **共享内存兼容**：Host 与 Sender 使用 64 字节 `HidBridge.Buttons.v1` 映射和同名 mutex。跨进程双进程夹具由主代理复核为 29/29；Host 在真实 COM13 收到 ButtonState 后发布到 MMF 的组件链路已验证。实测时 physical `valid=0`，尚未证明真实按钮输入能从实体鼠标到达 Sender。
- **软件平滑**：A5/UDP 与 Makcu 标准软件 MouseReport 已在 M 端统一进入 `m_udp_smoothing`，发往 P 的槽字段为 0；物理 raw 与专用原始报告注入路径保持原样。平滑总量、按钮最终态与真机效果仍待验收。
- **输入路径边界**：本次只改变普通非物理软件报告的平滑位置；不改物理鼠标 raw 转发、克隆流程或 `DIAG_REPORT_INJECT_REQUEST` 的字节语义。Python sender 与直连 Makcu sender 不在本轮实现范围。
- **不触发复位**：任何配套的 Python 只读核查工具都必须遵守 [AGENTS.md](../AGENTS.md) 的「串口查询默认不触发复位」（打开前置低 DTR/RTS），并用 `uptimeMilliseconds` 自证。
- **模式切换风险**：Makcu runtime 开启时暂停 ButtonState 上行，以免 A5 帧污染 V4 字节流；Host 在目标波特率重新查询并确认 M 角色和实际模式后才报告成功。COM13 实机 ON/OFF 与新波特率查询/角色复核已通过；失败恢复及物理输入转移尚无故障注入验收。
- **状态有效性**：共享内存对无效、断连、过期及未建立订阅的状态清除按钮位；Sender 的第三方按键选项默认关闭。实机检查期间所有物理 `valid=0`，目标鼠标描述符中五个按键位与 VK 对应关系仍未确认。
- **串口预算**：5 ms 是目标间隔，不是精确实时保证；约 2.17%@921600、17.36%@115200 是 8N1 理论占用，115200 Makcu 模式暂停状态推送。实机 409/2.391 s 计数受 Windows 批量串口读取影响，不作为精确频率；长期丢帧恢复和 1–2 ms 端到端延迟仍未验证。
