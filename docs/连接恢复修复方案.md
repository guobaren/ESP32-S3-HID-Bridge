## 2026-09-25 P 先连接且 H 带运动接入的拖尾专项计划

### 现象与证据边界

- 用户现场：先连接 P，保持鼠标快速移动，再连接 H；有概率出现约 1 秒的移动拖尾，按键响应也出现拖尾。用户反馈连接 M 的 UART 时未复现。
- 用户后续补充：先连接 H/M 的情形不复现；先连接 P、但连接 H 时 M 已连接的情形也不复现。这里保留用户的 H/M 表述，不擅自指定 H 与 M 的内部先后顺序。“M 已连接”沿用当前对话中的连接条件，仍需区分 M 的 UART/USB 物理接线、供电、端口打开与固件就绪，不能将几者视为同一状态。
- 范围修正：不能把所有 P 先连接场景都列为失败；当前重点是接入 H 的瞬间 M 是否已经连接及其启动状态。上述两组属于用户反馈的未复现对照，次数未知，不能标记完整验收 Pass。
- 当前结论：`Failed（间歇，用户反馈）`；主代理未复现。复现概率、试验次数、固件哈希、M/P 供电、UART 物理接线与串口端口打开状态、串口是否输出日志、是否有软件输入均未知。
- 现象只覆盖“P 先接、H 带运动接入”这一场景。不能外推为其他连接顺序、普通鼠标插拔、P/M 复位、R8 或整张 O1–O6 矩阵通过。
- 既有 `churn-P.log` 有短队列与较长输入断流同时出现的记录，并见 P 清理 58 次、挂载 12 次、peer timeout 15 次；`LINK_TIMEOUT` 从 750 ms 调到 3000 ms 的效果仍待验证。审计记录中，暂停写盘未消除当时的症状，否证的是该次对照中“暂停写盘即可解决”的假设；不能据此外推排除本次日志背压。以上都只是区分调查方向的证据，不能直接证明本次拖尾由 UART、清理、挂载、供电或日志引起；参考 `docs/交接.md:3-47` 与 `docs/审计.md` 的相应历史记录。

### 1. 主复现条件与变量控制

- 主验收条件是不连接 M 的 UART：先接 P，让鼠标持续快速移动，再接 H；重复并逐次记录是否出现约 1 秒拖尾以及按键响应延迟。
- 必须保留两组用户已报告未复现的对照：① H/M 先连接再接 P（分别记录 H、M 的实际先后）；② P 先连接，M 在 H 接入前已连接。各组保持相同鼠标运动与按键负载，记录 M 连接至 H 接入的间隔；将物理接线完成、上电、角色锁定、Host 就绪与端口打开分别打点。该对照用于识别 M 接入/启动时序差异，不直接证明供电、日志或队列为根因。
- 之后做条件对照：M UART 物理接线但不开端口；打开端口但不打印诊断内容；打开端口并输出低频诊断日志。分别记录“仅接线”和“打开串口”状态，不能把二者合并成“接了 UART”。
- 每次记录 M/P/H 的供电来源、电压/电源状态、共地、UART 线状态、串口配置、DTR/RTS 是否变化或触发复位、是否有软件输入注入、H 插入时鼠标运动和按键状态。当前这些条件均未知。
- 改变供电方式前先确认该接法符合板卡供电设计，并排除 USB/调试口之间的反向供电；一次只改变一个变量，其余线序、运动、负载和软件注入保持一致。UART 端口打开可能改变 DTR/RTS 或复位状态，必须单独标注。

### 2. 不扰动现场的证据采集

- 不为抓日志临时连接或打开 M UART，以免中断主要无 UART 复现条件；先尝试使用板载 RAM/flash 中已有的快照。
- 当前 `onboard_log.h` 暴露 `set_paused/flush/read`，没有冻结诊断快照 API。须先实现一个有界 RAM 环形快照和失败时冻结能力，再在失败后停止输入并冻结，事后导出；导出时记录是否打开串口、改变 DTR/RTS 或导致板卡复位。现有写盘/暂停日志本身可能影响实时性，不能视为无扰动证据。
- 高频同步打印可能制造或放大背压；实时主场景不启用高频日志。先保留低频阶段事件和计数，详细快照失败后再导出。

### 3. 待验证的竞争假设

- **未就绪期间运动积压并在挂载后回放：** H 插入或克隆设备重新挂载期间，输入已进入队列；USB ready 后依次发送旧运动，表现为停止移动后仍继续移动。
- **实体输入链路某段排队或消费停顿：** M 的 USB Host 回调进入 report 队列，由 `hid_host_mouse.c:650` 的 `raw_report_task` 消费，再经 UART1 TX/RX、P motion 队列及待提交状态到 USB submit/complete；找出最旧项年龄、队列峰值及哪一段生产/消费不匹配。P 入口和消费位置分别在 `pc_hid_output.c:1102` 与 `pc_hid_output.c:584`。当前原始路径不应只在 `on_mouse_report` 打点。
- **清理/重枚举或 peer timeout：** P 的重复 cleanup、mount、peer timeout 或 USB ready 状态变化可能造成断流；要与纯排队拖尾区分。记录 `mount/cleanup/peer_timeout/reset_reason/hb_gap`。
- **日志背压、调度和供电：** 分别作为独立假设，使用上节条件对照。历史暂停写盘对照只否证对应试验中的假设，不能证明本次写盘无影响，也不能把日志当作默认根因。
- 按键也拖尾意味着问题不一定是坐标平滑或只保留最新移动量；必须追踪按下/松开边沿和目标端报告完成。

### 4. 需要的时间与队列证据

- 每块板记录本地单调时钟、报告 sequence、generation/epoch、鼠标连接代号、H 插入、Host 枚举、Profile 安装/挂载、ACK、USB ready、停止移动、按下和松开事件。
- 每级队列记录当前/峰值深度、最旧项年龄、生产与消费速率、丢弃/溢出数量、背压次数；P 另记录 HID submit/complete 和 pending motion，M 记录 Host report 到 UART1 TX 的间隔与积压。
- 计算 H 插入→枚举→挂载→ACK 的同侧耗时，以及最后一个实际运动/按键边沿到目标端对应事件的延迟。两板单调时钟不能直接相减；没有同步时只比较同一侧的时间间隔和序号因果顺序。若确需跨板绝对延迟，先建立并记录时钟同步误差。
- 失败现场先冻结快照，再做任何串口连接、读出或复位；同时记录证据导出动作是否触发复位。分别比较 queue backlog、cleanup/mount、peer timeout 与 reset 事件的先后关系。

### 5. 只有证据支持后才实施的输入修复方向

- 若证实挂载前的旧运动在 ready 后追赶：ready 边界清除过期运动，并同步当前按键状态；未按住的按钮保持释放，不能丢失按下/松开安全边沿。
- ready 后采用有界队列和明确背压。不能为了降低拖尾而任意只保留最新相对位移，导致移动量丢失；不能跨按钮边沿合并报告；不能丢释放或安全帧；保留实体输入优先级。
- 在量出队列年龄和端到端延迟前，不先扩大缓冲、增加预积压或降低鼠标速度。10 秒是连接恢复上限，不是输入延迟合格线；先测稳定连接基线，再与用户确认/依据现有要求确定输入延迟阈值。约 1 秒拖尾明确不合格。
- 如果证据指向 cleanup、peer timeout、DTR/RTS reset 或供电，则分别修复对应因果链，不以输入平滑改动掩盖断流或复位。

### 6. 故障注入与专项验收

- 按用户既有要求优先以按键（点击）的按下/松开延迟判定，移动尾迹为补充；必要时使用同一录像或外部触发基准，不能把串口日志到达主机的时间直接当作无误差的物理事件时间。
- 本轮仅更新文档，没有执行采集、插拔、复位或刷写。后续实施若需用户动手，按现有约定先发声提醒；刷写或复位前须取得用户同意，保留故障现场。

- 逻辑/集成故障注入至少覆盖：H 未 ready 时持续输入并在 ready 后恢复；USB submit/complete 暂停后恢复；低频日志写入阻塞/背压；队列满时产生按下与松开边沿；每项记录队列峰值、最旧年龄、运动量守恒、按钮状态和结束时队列是否清空。
- 无 UART 主场景至少做 30 次探索性重复，逐次记录 `x/N`（出现拖尾次数/已执行次数）、约 1 秒拖尾是否发生、按键延迟、供电/线序和时间证据。`0/30` 仅表示本轮 30 次未复现，不是可靠性保证或根因排除。UART 物理接线但不开端口、开端口不打印、有日志打印的对照使用相同运动、供电和接入顺序，并单列 DTR/RTS 与复位差异。
- 分别回归静止状态插入 H、逆序连接、P/M reset、拔插期间按住后释放、实体与软件输入并发性能。该专项任何通过结果只覆盖其明确记录的条件，不代表其他矩阵项目全部通过。
- 状态保持 `待定位；专项修复未实施；实机专项未验证`，直到取得可复现证据、对应修复和复测结果。

## 目标与边界

让鼠标拔插、任一板复位及可恢复的 Profile 克隆失败能在有界时间内恢复，避免重复事件重做 USB 清理、迟到确认被错误拒绝、旧异步任务覆盖新 Profile，以及实体鼠标输入错误被当成物理断开。最终接线稳定后，端到端恢复上限为 10 秒；超过即记为 `Failed`。不支持的描述符等不可恢复错误应明确终止，不能承诺所有故障都能恢复。

当前 `FLOW_ACK` 已携带消息类型、`flow_id`、状态和双方 generation；`DEVICE_GONE` 已携带发送方/目标 generation、`event_id` 和原因（`firmware/dual_proxy/main/bridge_protocol.h:93-103`）。优先复用现有字段；实现前核对各报文是否足以隔离旧会话。若必须改变协议，同步更新 `docs/protocol.md`、两端编码/解析及测试，并将相同协议版本刷入两板。Host C# 输入协议与板间协议分别评估；仅在其实际受影响时同步修改 C# 编码器。本轮文档保存不改变任何实际协议。

## 身份与事务状态模型

这些标识各自解决不同问题，不得互相代替：

| 标识 | 生命周期与用途 | 允许的重用方式 |
| --- | --- | --- |
| 板卡 `generation` | 每块板每次启动生成；标记该端当前启动会话 | 只在该端新启动时改变；目标是让确认与当前会话绑定，不能假定所有现有 ACK 都已携带双方 generation |
| 鼠标连接代号 | M 在同一启动会话内，每次真实 Host 设备连接周期递增；区分拔插前后的物理设备状态 | 同一次连接周期的采集/发送共享；真正断开后不得沿用旧 Profile |
| `event_id` | 一次 `DEVICE_GONE` 断开清理事件 | 有界重试、重复到达和迟到 ACK 都沿用同一 `event_id`；新断开事件使用新 ID |
| `flow_id` | 一次 REQUEST/OFFER 清理与 Profile 协调事务 | 同一事务重试沿用；新事务分配新 ID |
| `transfer_id` | 一次完整 Profile 数据传输 | BEGIN、CHUNK、COMMIT 及其重放沿用同一 ID；新 Profile 传输使用新 ID |
| P 本地 `epoch` | 作废已经排队或已取出的旧 USB 重配置工作 | 只由 P 本地递增，不放入协议；任何异步步骤提交前都要校验 epoch 仍有效 |

M 与 P 显式记录事务阶段、当前身份对、活动鼠标连接代号和唯一活动 Profile 流。重试只重放同一事务，不创建新的 ID；结束、被新 generation/连接代号取代或超过预算后，旧 Profile 工作不得修改当前状态。例外是未完成的 GONE 清理屏障：快速插回产生新连接代号时仍须保留该屏障，直到其完成或对端重启使旧 USB 会话失效。

### 1. 固化 M/P 状态机和标识匹配

- 分别定义 M、P 的等待、采集、清理、传输、挂载、完成、可重试失败和最终超时状态。
- 统一检查 `(M generation, P generation, mouse connection id, event_id/flow_id, transfer_id, epoch)` 中适用于该消息的字段。
- 明确同一时刻只允许一个有效的断开屏障和一个 Profile 传输；重复帧只推进原事务，不启动第二次清理或安装。
- 为状态转移写纯逻辑测试，覆盖 ID 匹配、旧 epoch 作废和重复事件去重。

### 2. 让 `DEVICE_GONE` 清理确认可有界重试

- M 对同一个 `event_id` 在确认前按有界策略重发 `DEVICE_GONE`；重发沿用相同 generation、目标 generation 和 `event_id`。
- P 对已完成的同一事件返回同一结果，不再次卸载新设备；正在处理时将重复帧合并到同一清理任务。
- 在原事件仍有效、双方 generation 与 event ID 匹配时，接受有效的迟到 `FLOW_ACK`；不得仅因本地一次等待截止就使尚可匹配的 ACK 永久无效。快速插回不作废旧屏障，不能因此拒绝其迟到确认。
- 快速插回时允许 M 先枚举并采集新 Profile，但必须等待旧 `DEVICE_GONE` 清理屏障完成后才能启动其 OFFER/传输；旧事件不能清除新连接状态。

### 3. 让 P 清理失败后可以恢复

- P 清理失败时保持克隆门关闭并保留事务身份，允许同一 generation、同一事件的有限重试；不得永久拒绝同 generation 的后续恢复。
- 若 USB 清理已经成功但 `FLOW_ACK` 入队失败，只重试排队原 ACK；不得重复执行 USB 卸载、清除输入或增加 epoch。
- 每次清理/安装工作在副作用提交前后检查 epoch。旧 epoch 被取消后不得安装 Profile、改写活动描述符或回成功 ACK。
- 只有清理实际成功后才能发成功 `FLOW_ACK`；失败响应和重试次数必须可从低频日志区分。

### 4. 使 Profile 协调和传输可恢复

- P 的重复 `PROFILE_REQUEST` 由 M 按匹配 generation/`flow_id` 去重；同一活动事务不重复采集。物理鼠标尚未枚举时进入等待状态，待 Host 设备到达后再采集，不把“暂未枚举”直接定为永久失败。
- P 在应用层收到 `PROFILE_OFFER` 时先按事务 ID 去重，再排入异步清理；完成清理后才回 OFFER 的 `FLOW_ACK`。重复 OFFER 不得造成并发清理或让旧操作覆盖新 Profile。
- 对 `PROFILE_BEGIN/CHUNK/COMMIT` 提供幂等接收和有界重传：重复分片不重复计入，缺失分片可恢复，同一 `transfer_id` 的重复 COMMIT 返回已有处理结果。最终 `PROFILE_ACK` 丢失时，重放同一事务只补最终 ACK，不重新枚举 USB。
- 把不可克隆描述符、USB 卸载/安装失败、暂未枚举、队列暂时不可用、确认超时区分为可重试/不可重试原因，保留足以诊断的错误类别。
- 优先通过现有报文实现整份 Profile 的有界重传；若采用选择性补片或新增状态码，须先明确字段、兼容性与两端实现，再同步协议文档和测试。

### 5. 修正 M 的 HID 状态及输入错误路径

- M 收到与当前活动事务绑定的成功 `PROFILE_ACK` 后，将自己的 UART1 `usb_state` 更新为 `HID_CONNECTED`；失败或旧 ACK 不得更新状态。当前实现中的该报文为 17 字节，包含 `transfer_id`、CRC、status 和双方 generation（`firmware/dual_proxy/main/bridge_protocol.h:99-105`），收发两端均按此校验。此协议已发生版本变化，两板需同版运行；本次拖尾反馈所用固件哈希未知，不能断言现场运行的就是该版本。
- 将 `on_mouse_release(false)` 代表的输入释放/报告异常与 `on_mouse_release(true)` 代表的真实物理设备断开分开处理。前者释放按钮并记录输入错误，不触发 `DEVICE_GONE`、Profile 清理或 USB 重枚举；后者才开始物理断开事务。
- 覆盖物理按键、软件按钮和键盘按键在超时、断开、清理失败、退出时均会释放。

### 6. 落实 10 秒预算和诊断日志

- 从 M、P、H 最终接线稳定且触发条件成立时开始计时，直到 Windows 当前 PnP 节点恢复、G HUB 识别且实体输入可用；单独记录软件输入和释放结果。
- 重试间隔、次数和各阶段预算是**待实施后测定的参数**，当前没有经本方案验证的建议值。先用低频事务日志记录时间戳、双方 generation、鼠标连接代号、event/flow/transfer ID、状态转移、重试计数、epoch、错误类别和挂载结果；不记录高频鼠标帧。
- 各阶段共用剩余总预算，不能串联多个完整的 5 秒等待；无鼠标时正常等待，实际插入后开始该次恢复计时。预算耗尽后明确终止本轮，不无限循环；新物理事件或新会话可按清理规则重新发起。
- 已执行端到端测试时，耗时超过 10 秒、PnP 缺失、G HUB 未识别、移动/按键不符、未释放或无法取得预期实际结果均记为 `Failed`，并注明证据缺口。未执行的项目标记 `未验证`；构建、串口命令退出码或静态 PnP 不得代替功能验收。

### 7. 增加异步故障注入

逻辑/集成注入记录事件序列、注入点、重试次数、最终状态、残留队列、清理和安装次数；模拟结果不得声称 PnP/G HUB 通过。实机阶段再采集双板日志和实际 PnP/G HUB/输入结果及耗时。

| 注入场景 | 必须检查的结果 |
| --- | --- |
| 丢失 REQUEST ACK、REQUEST 早于鼠标枚举 | 同 flow ID 重试不重复采集；未枚举进入等待；设备到达后继续当前有效流程 |
| 丢失或迟到 `DEVICE_GONE` `FLOW_ACK` | 同一 `event_id` 有界重试；有效迟到 ACK 可完成同一事件；不会重复清理新设备 |
| P 清理失败后再次成功 | 克隆门保持关闭直至清理成功；同 generation 可恢复；成功 ACK 在实际清理之后 |
| 清理完成但 ACK 入队失败 | 只补发 ACK，不重复卸载、释放或重置新 Profile |
| H 快速拔出/插回与旧事件并发 | 新连接先采集可用 Profile，旧 GONE 屏障完成前不发 OFFER；旧事件不覆盖新连接 |
| P 或 M 在各事务阶段复位 | 旧 generation/epoch 的 ACK、Profile 和任务全部失效；新会话能在预算内建立新流程 |
| 重复 OFFER、BEGIN、CHUNK、COMMIT | 单事务去重；重复输入不造成多次 USB 重枚举或重复分片 |
| 丢失最终 `PROFILE_ACK` | 同一 transfer 的有限重试只补 ACK；不再次 detach/attach |
| 不支持的描述符/挂载失败 | 返回可区分终态；释放输入；保留错误类别，不把不可克隆误报为超时 |
| `on_mouse_release(false)` 输入错误 | 释放受影响输入，不产生 GONE、克隆清理或 USB 重枚举 |

## 已审查缺口的处理结果（本轮）

原缺口位置保留如下，括号内为本轮处理结果：

- `uart1_link.c` 的 FLOW_ACK 超时终止（原文 966-1001）：改为 `link_flow_t` 事务 + `link_flow_poll()` 有界重发；GONE、REQUEST、OFFER、COMMIT 都在同一 generation 内重放同一 ID，只有截止时间/次数预算用尽才终止。
- `uart1_link.c` 的 GONE 确认/失败/新 Profile 排队缺口（原文 521-540,1438-1456）：同一 `event_id` 最多重发 8 次；P 报 FAILED 不再永久作废；`s_gone_completed_*` 记住最近事件，匹配的迟到 ACCEPTED 可重新开放克隆门；`link_gone_keeps_existing_event()` 保证快速插回沿用原事件。
- `dual_proxy_app.c` 的异步清理去重与“清理成功后才 ACK”（原文 231-303）：`dual_pc_hid_schedule_disconnect()` 的 `duplicate_completed` 分支只补发确认；`pc_hid_output.c` 在清理成功后立刻登记结果再尝试 ACK。
- `pc_hid_output.c` 的清理失败/ACK 入队失败/同 generation 恢复（原文 1447-1492,1795-1902）：清理失败本地重试 3 次；清理成功但 ACK 入队失败时只补发 ACK；清理失败不再永久拒绝同 generation 的后续恢复。
