# 问题档案：一次点击被上报成两次（单击重复）

- 状态：**P 端 raw 输入单 FIFO 已部署到 P/COM13 与 M/COM3 同镜像；运行状态已核对，单击重复量化验收未完成**（2026-10-14）
- 影响面：仅影响桥接链路（物理鼠标经 M/P 双板转发）；鼠标直插目标电脑无此现象
- 证据目录：`artifacts/tests/click-dup-20261014/`
- 本轮部署证据：`artifacts/tests/pc-input-fifo-deploy-preflight-20261014-184007/`（write manifest、P/M 脱敏启动日志、R1/R2 只读 stats 与 runtime manifest）
- 一句话结论：**修复前的 P 端双 FIFO 与跨队列等待是当前最受证据支持的状态次序异常机制；代码已把 P raw 输入合并到单一 128 槽 FIFO，并已部署到两板同一镜像。**运行快照确认 P 的 ID 10 单 FIFO、ID 11 全零兼容槽及 ID 12 控制队列字段符合当前设计；用户短时反馈“暂未发现额外点击”。但没有独立操作计数、PC 事件记录或设备级边沿对照，不能判定单击重复已修复。握手/厂商突发跳过仍可能丢报告，队满仍可丢输入；端点 owner、按钮 overlay、force/generation 等方案未实施。第二轮原始 body 样例支持提交状态与最新 RX 状态不一致，但不能把每条 SUB 精确映射到唯一 RX 事件，也不能仅凭最新状态差判乱序。

## 1. 现象与复现条件

- 现象：**一边移动鼠标一边点击按键**时，有几率被目标电脑识别为两次按下（时间轴上表现为"释放→按下"的幽灵点击）。
- 必须"边移动边点击"：静止状态点击不触发。
- 鼠标直插目标电脑时无此问题，说明问题由桥接链路引入。
- 用户主观描述为"有几率"；实测比例见第 2 节。

## 2. 影响量化

| 来源 | 测量方式 | 结果 |
| --- | --- | --- |
| 目标电脑侧 | `tools/measure_click_timing.py`，2,315,746 Hz 采样左键约 120 秒 | 75 个记录区间中 **18 个短区间**（0.9~11.7 ms，低于 15 ms）= **24%**；其余 57 个区间为 76.1~190.0 ms |
| 同上，物理动作计数边界 | 75 个完整记录区间减去 18 个短区间，得到 57 个非短区间 | 未取得独立物理动作计数；`18/57≈32%` 仅是把 57 个非短区间假设为 57 次实际操作时的条件估算 |
| P 板侧 | 三层诊断流对照（第二轮，74 个按住段） | 按住段内夹零比例 **RX 0.0% / SUB 24.3% / COMP 23.0%** |
| P 板侧 | 状态不一致候选计数（最新 RX 已释放时 SUB 为 `buttons!=0`，event_id 口径；非逐事件确认，最新 RX 状态差也可能是正常排队延迟） | 第一轮 SUB 82 / COMP 174 次；第二轮 SUB 63 / COMP 82 次 |

目标电脑侧 24% 与板侧 COMP 23% 来自**互不相关的采集路径**，量级吻合，但这种量级吻合不是逐次点击的跨设备配对证明。采样结束时仍有一段未完成的按下状态，不能把它当作完整点击。

## 3. 根因

### 3.1 P 端分流与消费等待（修复前代码状态）

以下是单击重复原始采集时的代码状态，不应读成当前实现：2026-10-14 本轮已将 P raw 输入改为单一 128 槽 FIFO。原来的两队列分流和跨队列等待已从源码移除；当前部署与队列运行字段已核对，但尚无生产路径 fixture 或实机逐边沿量化复测结果。

1. 分流：`firmware/main/pc_hid_output.c:1796-1851`
   P 板入口按 `data[0] == 0U`（是否带按键）把 `RAW_HID_INPUT` 分到两条队列；这不是完整的 interface + Report ID + 动态布局分类：
   - `data[0] == 0`（纯移动、以及真实的释放报告）→ `s_motion_input_queue`
   - `data[0] != 0`（按下报告）→ `s_vendor_input_queue`

   当时两条队列各 128 槽。当前只有一个 128 槽 raw 输入 FIFO；统计协议 ID 10 记录该队列，ID 11 保留为全零兼容行，ID 12 的 vendor control 队列仍独立。

2. 消费等待与优先级：`firmware/main/pc_hid_output.c:1062-1107`
   修复前，`vendor_input_task` 发现 vendor 队列为空后，会阻塞等待 motion 队列，最长 10 ms。等待 motion 的接收不会被新到来的 vendor 按下报告唤醒；若随后 motion 释放报告唤醒任务，任务可直接消费释放而不重新检查 vendor。该等待盲区与双 FIFO 共同提供释放先于按下提交的路径。当前消费者只等待并接收统一 raw FIFO，因此这一跨队列等待盲区已移除。

   3. 可解释的后果：两条队列都源自同一输入流，却不再共享 FIFO。报告进入不同队列后，按下可滞留而释放先提交；第二轮样例中的状态顺序与此机制相符。这是目前最受证据支持的主因，但不表示已证明每一份延后报告的唯一来源事件；当前尚未完成修复后验收。

### 3.2 时序示意（实测帧，第二轮 `event_id` 375606~375620）

```
 -8.413  RX   375606  buttons=1   ← M 送来「按下」
 -6.728  RX   375607  buttons=1   ← M 送来「按下」
 -0.894  RX   375609  buttons=0   ← M 开始持续送「释放」
 -0.527  RX   375610  buttons=0
 -0.393  RX   375611  buttons=0
 +0.000  SUB  375612  buttons=0   ← P 提交「释放」✓
  +1.264  SUB  375615  buttons=1   ← RX 状态已释放时，P 又提交按下状态
  +2.230  SUB  375617  buttons=1   ← 再提交按下状态
 +3.229  SUB  375620  buttons=0
```

该窗口呈现约 **9.7 ms** 的按下/释放状态差，支持“队列延迟后提交”的解释，其时长与实测短区间相符。此处应称为**状态不一致候选**，不是已确认幽灵按下：相同 body 可重复出现，诊断流有丢弃，且最新 RX 状态与 SUB 不同也可能只是正常排队延迟。因此不能据此精确配对某个 SUB 报告与唯一 RX 事件，也不能单凭最新状态差异判定乱序。

### 3.3 M 板与链路侧：未见同类乱序证据，但尚未完全排除

- 当前活动的物理 raw-task 路径在 `firmware/main/hid_host_mouse.c:1577-1581` 调用发送；这不是全工程“唯一发送点”的证明，也不证明每个物理输入都成功入队或送达。M 侧输入队列可能溢出（`firmware/main/hid_host_mouse.c:863-907`）。
- `firmware/main/uart1_link.c:1296-1311` 将已入 UART1 motion 队列的 `RAW_HID_INPUT` 按 FIFO 消费；队满会丢弃/返回超时（约 `:1337-1380`），输入报告没有重发。故只能说已入队项目按队列顺序发送，不能推成端到端不丢失或全链路顺序已排除。
- 有界重发覆盖 PROFILE / GONE / COMMIT 等控制流帧，不覆盖输入报告；这排除了“输入帧由重传机制主动复制”这一具体解释，但不能排除队列溢出或其他路径影响。

## 4. 候选解释与当前证据

| 候选 | 当前证据与边界 |
| --- | --- |
| M 板重复发送同一报告 | 活动 raw-task 路径有一处发送调用，但 M 队列丢弃、重复 body 的来源和逐帧身份未完全核验；**未完全排除** |

| M 板队列乱序 | 已入 motion FIFO 的输入按序消费；队列溢出/其他 producer 到该 FIFO 前的行为不等于端到端不丢失，**尚无独立实机逐帧证据排除全部 M 侧影响** |
| 合成路径与透传并存 | `dual_uart1_send_mouse` 存在于 `dual_proxy_app.c:684`，但该 `on_mouse_report` 回调不是当前物理 raw-task 路径；旧文档引用的 `dual_uart1_send_physical_mouse` 不存在。当前样例不能充分排除软件合成与物理透传交互 |
| 物理鼠标自身抖动 | RX 侧观测到的段内夹零较少（0~1 段），不支持其为该样例主因；但有丢弃且无独立设备级边沿记录，不能把所有源侧影响绝对排除 |

## 5. 证据有效性边界

- 诊断流的 `captured` / `dropped` 是**开机累计值**（`firmware/main/diag_stream.c:130-137`：队列已存在时 `dual_diag_stream_start` 直接返回、不重置）。第一轮新增生成 359,137，捕获 171,711、丢弃 187,426，丢弃率 **52.19%**。第二轮起点为 171,711 / 187,426，终点为 356,426 / 207,270；增量捕获 184,715、增量丢弃 19,844，生成 204,559，丢弃率 **9.70%**。第二轮 JSONL 有 184,714 条，较 captured 增量少 1 条，按边界差异保留，不强行抹平。
- 丢弃会改变状态段切分、分母和跨层可观察关系；漏掉中间状态可能把相邻段合并，也可能让比率以其他方式偏移。因此 24.3% / 23.0% 不能笼统称为数学下界。
- 第二轮表格中的 63/82 是按最新 RX 状态判出的状态不一致候选，不是逐事件来源配对后的已确认幽灵按下。总体丢弃率无法用于估算具体假阳性个数；最新 RX 与 SUB 的暂时差异也可能来自正常排队延迟。
- 第一轮 SUB 绝对计数不可用（拥塞时任务上下文记录的 `P_USB_REPORT_SUBMIT` 丢得更多：40031，对比 COMP 67255、RX 61145），只能用其结构判据。
- `event_id` 与时间戳必须分开报告。两轮按 `event_id` 顺序的时间戳回退均为 0，但两个判据的计数并不完全一致：第一轮 COMP 为 174 / 176；第二轮 SUB 为 63 / 64、COMP 为 82 / 83（分别为 id / ts 口径）。因此不能写成结论完全一致；保留两种口径及其差异。
- 当前分析固定面向本次鼠标样本：RX/SUB 使用接口/实例、Report ID 与长度筛选，SUB 检查提交成功字段；COMP 解码缺少等价的 instance 过滤，且允许无 Report ID 的 8 字节 body。不能把当前固定布局过滤描述成对任意接口/Report ID 的通用验证。

## 6. 修复方案与实施状态

截至 2026-10-14，本轮实现并部署 §6.1 的 P raw 输入单 FIFO 子项。其余 owner、按钮来源叠加、force/generation、有界拥塞与低带宽诊断设计仍待实施。当前 128 槽队列满时仍会丢报告；现有 clone-ready/厂商突发分类跳过与 endpoint 重试策略也未在本轮改变，不能声称按下/释放边沿已受保护。

### 6.1 输入报告单一有序 FIFO

- **已实现（源码范围）**：通过现有解析/session 校验且未被握手/厂商突发策略跳过的 raw input item，一次入同一 128 槽 FIFO；消费者只从该 FIFO 按顺序取出，不按 buttons 是否为零分队、不把按键报告置队首。移除了“vendor 队列空时等待 motion 队列最多 10 ms”的竞态。
- **已实现（保真范围）**：队列项仍携带完整 report body、Report ID、interface、长度、session generation、时间戳及分类标记；不合并、不压缩、不改 UART wire 格式。统计协议 ID 10 报告统一 raw 队列；旧 ID 11 仍输出容量、深度、peak 和计数全零以保持统计记录格式，ID 12 的 vendor control 队列独立不变。
- **已部署运行（有限范围）**：2026-10-14 18:47 P/COM13、M/COM3 依次写入同一镜像，app 445,296 B、SHA-256 `70E93F20690B1E687F9830230DC6EDBFF54CB36E2E60DBAF8703647C87A3B734`；每板三段写入 exit=0 且各有 3 条 `Hash of data verified`。按用户要求未备份 fullflash、未执行 `erase-all`。安全 R1/R2 相隔约 33.5 秒，uptime 连续；P `mounted_acked=true`，ID 10 capacity=128、depth=0、peak=17、received=29,544、dropped=0，ID 11 所有字段全零，ID 12 capacity=128、received=470。P aggregate `vendor_dropped=66` 两次不变，与 ID 10 队列计数口径不同。M `connected=true`、`profileReady=true`，input/heartbeat 计数增长。详细证据见 `artifacts/tests/pc-input-fifo-deploy-preflight-20261014-184007/runtime/postflash-runtime-manifest.json`、`runtime/P-R1.json`、`runtime/P-R2.json`、`runtime/M-R1.json`、`runtime/M-R2.json` 及部署/脱敏启动日志。
- **用户短时体验**：用户反馈“暂未发现额外点击”；未记录测试时长、独立点击动作数或设备级边沿，因此是定性观察，不是量化通过结论。
- **仍待验证/有边界**：没有调用生产 `pc_hid_output.c` 入队/消费路径的专用 fixture；上述实机数据证明镜像写入、启动和所报队列/链路状态，不证明 PC 侧点击结果或逐边沿顺序。既有 clone-ready/厂商突发分类跳过与 endpoint retry 未改，可能丢输入或释放；队满的 128 槽 FIFO 可丢任何 raw item。不能把“同 FIFO 入队”表述为端到端每边沿必达，也不能称单击重复问题已修复。
- vendor control 事务仍走独立队列；但现有 raw consumer 在处理需等待克隆就绪的输入项时仍可能等待最多 5 秒并阻塞同一 FIFO 后续报告。本轮保留该握手语义，未验证或解决这一队头阻塞风险。

### 6.2 单一端点发送 owner 与状态提交

- raw、synthetic、force 输出经单一 endpoint owner 串行仲裁；区分“已排队”“已成功提交”和“已完成”，不能把排队或忙时重试当作提交成功。
- 只有 USB 成功提交后才更新已提交状态与合成基底；合成报告不得在更早的 raw 尚未提交时读到未来模板。队列中的候选状态与 endpoint 已提交状态分开维护。
- raw 与 synthetic 输出的有效按钮状态都按**物理按钮状态 OR 软件按钮状态**组成。软件 overlay 只作用于现有软件映射位，并保留所有动态物理按钮位，包括 8 位以上按钮及非字节对齐字段；状态容器应使用按 layout 大小的 bitset/bitmap，不能截断为 `uint8_t`；后续 raw 不得清掉仍按住的软件键。
- synthetic 相对轴仅携带该次软件增量，不能从物理模板重放旧位移或滚轮。raw 的其余字段与动态 layout 语义保持完整。

### 6.3 release、force barrier 与会话代际

- 普通 software release 只撤销软件映射位；真正 all-release 按当前 layout 的 `button_count` 清除全部按钮位。普通 overlay 不承担全清职责。
- force-only 进入新 generation/barrier，清理旧 pending、队列、模板和按钮来源状态，并禁止旧代报告在释放后重播。停止转发/失联必须进入禁止转发状态；P 队列清空本身不能证明 M 端在途 raw 已清除。
- 按钮来源、layout、模板和 session 状态必须属于同一 session/generation/layout 版本；切换配置或重建会话时不得混用旧 layout 状态。恢复转发需等新 session/generation 的有效输入及明确同步策略；必要时先提交全释放，再接受当前合法状态。会话重建完成前不得消费旧模板。若现有跨板标识无法分辨旧代在途输入，需要另行设计并同步更新串口协议、C 编解码器和文档；本方案不暗中引入 wire 变更。
- force 清理与 release 提交失败必须显式失败，不报告成功；物理 USB 已断开时，无法保证对端实际收到释放报告。

### 6.4 有界拥塞与相对轴

- 对 endpoint busy 和正常拥塞保留按下/释放边沿，并定义有界故障窗口，避免无限阻塞。超过窗口即失败、停止转发、废弃旧 generation；USB 可用后优先提交全释放再恢复。
- 仅可合并已证明不会改变完整按钮状态的相邻兼容相对轴报告；合并时累加 X/Y、wheel 与 pan 增量。安全策略与测试完成前不启用合并。
- 队列满、UART 丢弃、endpoint 超时都必须可观测；不得以“提交尝试过”当作成功，也不得承诺故障断连时对端一定收到 release。

### 6.5 本地低带宽诊断

- 如需定位 P 端队列/endpoint 次序，记录 P 本地 `ingress_seq`、`submit_seq`、session generation、raw/synthetic/force 来源；queue item 与 endpoint inflight 元数据继续传到 complete 事件。这样可在 P 本地对照接收、提交和完成顺序，不需要先改变 UART 协议，也不只依赖“最新 RX 按钮状态”。
- 边沿记录包含初始状态和完整动态按钮位；同时保留非按钮字段异常、busy、失败、队列丢弃和 overflow 计数。诊断只降低逐帧日志负担，不能掩盖丢弃或把缺失事件补成成功。

2. **构建**：按项目规则构建当前 `firmware/` 主工程并记录实际输出。本轮 `sdkconfig` 的 `CONFIG_DUAL_PROXY_USE_CHERRYUSB=y`；已有 `build-cherryusb` 配置同样启用 CherryUSB，不代表第二种后端，本轮只构建了主工程一次。离线 fixture/build 仅证明相应软件层，不等于真实链路通过。
3. **同窗实机**：PC 端操作计数、M/P 两端报告/队列计数和 uptime 同窗采集；首尾 uptime 连续增长且墙钟增量相符，相关队列/诊断 `Δdropped=0`，完整重组报告逐项对应，无新增、缺失或倒序边沿；release 最终全零。已执行测试但必需输出缺失、数据不符或无法逐项比较，判 `Failed`；测试未执行或设备不可访问，标 `未验证`，不混用。
4. 覆盖静止/移动单击、长按、真实双击、侧键、滚轮、软件输入并发、断连停止、厂商交互和正常高 report rate。低速窗口只能作证据对照，不能代表高负载验收。
5. Windows `GetAsyncKeyState` 的短 click 采样只作辅助；设备区分的事件记录和实际操作计数应相互校验。不能仅凭短点击为零或三层段数相同就判 Pass。

## 8. 复现与分析方法

```powershell
# 终端 A（板侧采集机），采集前分别读取可见且已确认角色的 M/P uptime。
# 记录本机墙钟；read_device_stats.py 在 open 前后置低 DTR/RTS。
python tools/read_device_stats.py --port <M的COM> --baud 921600
python tools/read_device_stats.py --port <P的COM> --baud 921600

# 终端 A：启动 240 秒板侧窗口，记下开始墙钟时刻 T0。
# dual_uart_inspect.py 在串口 open 前后置低 DTR/RTS。
python tools/dual_uart_inspect.py --ports <P的COM> --seconds 240 --status-interval 5 `
  --outdir artifacts/tests/<日期> --tag click-dup
```

```powershell
# 终端 B（P 板作为 HID 设备连接的目标电脑），在终端 A 的 240 秒窗口开始后立即启动，
# 确保完整 120 秒 PC 采样落在板侧窗口内。两机分别记录墙钟起止时刻，并独立记录实际操作数。
python tools/measure_click_timing.py --seconds 120
```

```powershell
# 终端 A：板侧窗口结束后记录 T1，再分别读取 M/P uptime。若 M 串口不可访问，M uptime 标未验证。
python tools/read_device_stats.py --port <M的COM> --baud 921600
python tools/read_device_stats.py --port <P的COM> --baud 921600

# 离线分析
python tools/cross_check_state.py <jsonl>          # id/ts 双判据 + 判据前提检查
python tools/dump_click_window.py <jsonl> --span-ms 25   # 按时间轴摊开逐帧
python tools/diag_drop_profile.py <jsonl> --bucket-s 20  # 丢弃率的时间分布
python tools/trace_click_dup.py <jsonl> --out report.txt # 三层交错追踪
```

第二轮缓慢移动的低速窗口实测丢弃率约 **9.70%**；这不是 `<10%` 的保证，也不是高 report rate 验收。最终 `Δdropped=0` 需另用低带宽按钮边沿诊断，并仍需保留队列错误/丢弃计数。

`dual_uart_inspect.py` 和上述安全串口打开方式本身不证明查询期间未复位；每次窗口都要比较 M/P 首尾 `uptimeMilliseconds` 与墙钟增量。uptime 回退、归零或明显偏小表示发生了复位，跨复位累计计数必须切分，只能解释为复位后窗口。PC 120 秒采样必须与板侧 240 秒采集同步重叠，不可等板侧采集结束后再顺序运行。若某板的 uptime 或关键输出无法取得，应按实测失败/未验证边界分别记录。
