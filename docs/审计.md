## Known Issues

- `firmware/main/esp_hid_gap.c:923-933,1144-1160,1354-1381`：存在绑定设备定向重连 24 轮策略；中心端未响应时会增加约 30 s 连接等待，断线后会再次装填预算，尚未修复。
- `firmware/main/esp_hid_gap.c`：当前日志没有记录定向目标地址、广播模式切换和 Windows 中心端状态，无法把地址/RPA 问题与中心端扫描问题区分开。
- `firmware/main/usb_output_liveness.h:13`、`firmware/main/hid_output.c:638-662`：没有独立 native-USB VBUS 检测，只能用 3000 ms 枚举宽限期判断 USB 初始可用性；超时设备可能误转 BLE。
- `firmware/main/output_mode_selector.c`、`firmware/main/output_router.c`：策略测试已通过，但当前版本 USB/BLE 插拔顺序仍缺真实设备矩阵证据。
- `D:\YOLO_Project\esp32_move.py:11-19`：外部发送端仍可能发送全零 UDP 命令，Bridge 拒绝是协议正确行为；发送端应跳过无效报文并自行限流。
- `host/HidBridge.Host` 与接收目标之间没有 HID 报告应用回读；Host/固件传输成功不能单独证明目标窗口实际消费报告。
- `D:\ESP32-S3-HID-Bridge-worktrees\input-latency-telemetry`：受保护 worktree 当前登记为 `prunable`，含历史用户改动；不得删除或重置，需由后续维护者单独处理。

## 技术债

- `firmware/cmake/nimble_gap_peripheral_connect_compat.cmake` 依赖 ESP-IDF v6.0.2 源码锚点，升级 SDK 时必须重新审查。
- BLE 诊断缺少中心端和目标端时间线；后续应为每轮广播、目标地址、连接、加密、HID 就绪和断线原因增加可关联的短日志。
- 本机刷写 API 是固定路由的最小 HTTP/1.1 实现，只允许 Loopback；若扩大到上传、公网或复杂认证，必须更换成熟服务器和权限模型。
- 仓库未配置 Lint 和覆盖率，质量结论依赖 Build、Format、自动化检查和分层真实验收。
